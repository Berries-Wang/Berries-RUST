## 一、学习目标

学完后能够用源码回答以下问题（每阶段末的自检以它们为验收标准）:

| # | 问题 | 答案所在的层 |
|-|-|-|
| 1 | `Copy`、`Clone`、`Drop`、`Deref` 的规则定义在哪个文件？ | 语言语义层（`library/core`） |
| 2 | `Box`/`Rc`/`Arc`/`Vec` 的所有权与释放逻辑长什么样？ | 标准库实例层（`library/alloc`） |
| 3 | 编译器在哪一步判定"这里发生了 move"？ | 编译器前端（`rustc_hir_typeck` + MIR） |
| 4 | "离开作用域调用 drop" 是编译器哪个环节插进去的？最终代码长什么样？ | MIR 构建 + drop 展开（`rustc_mir_build`、`rustc_mir_transform`） |
| 5 | "一个 `&mut` 或多个 `&`" 的冲突判定函数在哪？ | 借用检查器（`places_conflict.rs`） |
| 6 | E0382 / E0502 / E0597 错误从哪个文件报出？ | 借用检查器诊断（`rustc_borrowck/diagnostics`） |
| 7 | NLL（非词法生命周期）比旧词法借用检查精确在哪？ | `region_infer` vs `lexical_region_resolve` 对照 |
| 8 | Polonius 是什么？和 NLL 的区别？ | 新一代算法（`rustc_borrowck/polonius` + 外部仓库） |

## 二、学习路线（四个阶段，建议 6~8 周）

```
阶段1 语言语义层(library) → 阶段2 编译器前端(HIR→MIR) → 阶段3 借用检查器(borrowck) → 阶段4 实验与前沿(Polonius/Miri)
     规则是什么              move/drop 在哪出生             规则怎么强制执行                新算法与验证工具
```

### 全景图：一段代码在编译器中走过的路（与四个阶段的对应关系）

```txt
   源码程序:   let s = String::from("hi");   let r = &s;
        │
        ▼ ─── 阶段2: 编译器前端 ─────────────────────────────────────
   [HIR 类型检查]        rustc_hir_typeck/expr_use_visitor.rs
        │                每个表达式被归类: Consume(move)/Borrow/Mutate
        ▼
   [MIR 构建]            rustc_mir_build/builder/scope.rs
        │                离开作用域 → 插入 Terminator::Drop (drop 初次落点)
        ▼ ─── 阶段3: 借用检查器 NLL ─────────────────────────────────
   [借用检查]            rustc_borrowck/nll.rs  三段式:
        │                ① 收集借用 + 冲突判定   places_conflict.rs
        │                   → "一个 &mut 或 多个 &" 规则
        │                ② 生命周期约束求解       region_infer/
        │                   → "借用不超出生命周期" 规则
        │                ③ 报错                  diagnostics/
        │                   → E0382 / E0502 / E0597
        ▼ 检查通过
   [drop 展开]           rustc_mir_transform/elaborate_drops.rs
        │                按 move 数据流把 Drop 精确展开为 分支+drop调用
        ▼
   [代码生成]            机器码中可见 __rust_alloc / __rust_dealloc
                        (笔记 001 的 cargo asm 实验验证的就是这一层)

   ─── 阶段1: library/core + library/alloc 是上面所有站点共同依据的
        "规则本体" (Copy/Clone/Drop/Deref/Box/Rc...)
   ─── 阶段4: Polonius/Miri 是 ①②③ 的替代算法与运行时验证方案
```

### 阶段 1（第 1~2 周）：语言语义层 —— 把规则读成 trait

**目标**: 明白所有权不是黑盒，是几个 trait + 编译器内建行为（auto trait、drop glue）的组合。

**核心判定图：一个值被使用时到底发生什么**

```txt
              值被使用 (赋值 / 传参 / 返回)
                        │
                        ▼
              类型实现了 Copy ?  ──是──►  位拷贝, 原值仍有效
                        │                 (i32 / &T / bool ...)
                        │否
                        ▼
              转移所有权 (move) ? ──是──►  所有权转移给新变量
                        │                 原值失效, 再用报 E0382
                        │否, 只想访问
                        ▼
                 借用 (borrow)
                 ├─ &T   共享借用: 可同时存在多个, 只读
                 └─ &mut 独占借用: 同一时刻仅一个,
                          且不能与任何 & 共存 (否则 E0502)
                        │
                        ▼
        所有者离开作用域 且 值未被 move / forget ?
                 ──是──►  编译器插入 drop
                          Drop::drop → drop glue → 释放堆内存
                 ──否──►  什么都不做 (值已属新主人 / 已泄漏)
```

**核心源码**（详见地图 003 的 A、B 两层）:

| 顺序 | 源码文件（本仓库，点击跳转） | 任务 |
|-|-|-|
| 1 | [`library/core/src/marker.rs`](../../library/core/src/marker.rs) | 读 `Copy`/`Sized`/`PhantomData` 的文档注释 |
| 2 | [`library/core/src/clone.rs`](../../library/core/src/clone.rs) | 对比 `Clone` 与 `Copy` |
| 3 | [`library/core/src/ops/drop.rs`](../../library/core/src/ops/drop.rs) | 读 `Drop` 的文档（为何无法手动调用） |
| 4 | [`library/core/src/ops/deref.rs`](../../library/core/src/ops/deref.rs) | 理解自动解引用 → 隐式重借用 |
| 5 | [`library/core/src/mem/mod.rs`](../../library/core/src/mem/mod.rs) | `forget`/`take`/`replace`/`swap` |
| 6 | [`library/alloc/src/boxed.rs`](../../library/alloc/src/boxed.rs) | **精读** `Drop for Box` 的释放顺序 |
| 7 | [`library/alloc/src/rc.rs`](../../library/alloc/src/rc.rs) | `Clone`（加计数）/`Drop`（减计数）与 `Weak` |

**动手实验**:
1. 用 `cargo asm`（见笔记 001 "分析工具"一节）观察 `String` 离开作用域时生成的 `__rust_dealloc` 调用
2. 用 `mem::forget` + `ManuallyDrop` 制造泄漏，用工具确认内存未释放
3. 手写 `MyBox<T>`（实现 `Deref`/`DerefMut`/`Drop`），对照源码验证行为

**自检问题**: 为什么实现 `Drop` 的类型不能 `Copy`？（marker.rs / drop.rs 里的约束与文档）；`&T` 是 `Copy` 而 `&mut T` 不是，在源码哪里体现？

### 阶段 2（第 3~4 周）：编译器前端 —— 找到 move 与 drop 的出生地

**目标**: 跟踪一段代码从 HIR 到 MIR 的旅程，回答"编译器在哪一步知道发生了 move"。

**核心源码**（详见地图 003 的 C 层）:

| 2 | [`compiler/rustc_hir_typeck/src/expr_use_visitor.rs`](../../compiler/rustc_hir_typeck/src/expr_use_visitor.rs) | **精读**: 表达式如何被归类为 `Consume`/`Borrow` |

**动手实验**:
1. 查看 MIR（观察 `Terminator::Drop`、`StorageDead`、move 标注）:

3. 用 `-Zdump-mir=main -Zdump-mir-graphviz` 生成数据流图并查看

**自检问题**: `let s2 = s1;` 之后再用 `s1`，报错发生在类型检查阶段还是借用检查阶段？（提示: 两处都参与，职责不同）

### 阶段 3（第 5~7 周）：借用检查器核心 —— `rustc_borrowck`（主战场）

**目标**: 完整理解 NLL 流程（约束生成 → 区域求解 → 错误报告），能定位任意借用错误的报出点。

**核心源码**（详见地图 003 的 D、E、F 三层）:

| 顺序 | 源码文件（本仓库，点击跳转） | 任务 |
|-|-|-|
| 1 | [`compiler/rustc_borrowck/src/lib.rs`](../../compiler/rustc_borrowck/src/lib.rs) | **先读模块级注释**: 全景鸟瞰图 |
| 2 | [`compiler/rustc_borrowck/src/nll.rs`](../../compiler/rustc_borrowck/src/nll.rs) | 三段式主流程 |
| 3 | [`compiler/rustc_borrowck/src/borrow_set.rs`](../../compiler/rustc_borrowck/src/borrow_set.rs) | 借用收集 + two-phase borrow |
| 4 | [`compiler/rustc_borrowck/src/places_conflict.rs`](../../compiler/rustc_borrowck/src/places_conflict.rs) | **精读**: 借用冲突判定（规则 1 的实现） |
| 5 | [`compiler/rustc_borrowck/src/type_check/mod.rs`](../../compiler/rustc_borrowck/src/type_check/mod.rs) | 约束生成 |
| 6 | [`compiler/rustc_borrowck/src/region_infer/mod.rs`](../../compiler/rustc_borrowck/src/region_infer/mod.rs) | **精读**: 区域约束求解（规则 2: 借用不超生命周期的实现） |

| 8 | 对照: [`compiler/rustc_infer/src/infer/lexical_region_resolve/mod.rs`](../../compiler/rustc_infer/src/infer/lexical_region_resolve/mod.rs) | 旧词法算法，体会 NLL 精确在哪 |
| 9 | [`compiler/rustc_mir_transform/src/elaborate_drops.rs`](../../compiler/rustc_mir_transform/src/elaborate_drops.rs) | drop 最终展开成什么样的代码 |

**动手实验**:
1. 分别构造 E0382、E0502、E0597 三个错误，然后用错误号反查源码:
   ```bash
   rg "E0502" compiler/rustc_borrowck/src/
   rustc --explain E0502
   ```
2. 用 `-Zdump-mir` 查看 borrowck 前后的 MIR 差异（drop 展开）
3. 夜间版对比: `RUSTFLAGS="-Zpolonius" cargo +nightly build`，观察错误信息变化

**自检问题**: 为什么 `if s.len() > 0 { return &s; }` 这类"条件性返回借用"词法借用检查会拒绝而 NLL 能通过？冲突判定的输入是哪两个借用？RegionInference 求解出的"区域"代表什么？

### 阶段 4（第 8 周）：实验与前沿 —— Polonius / Miri / 别名模型

**目标**: 了解借用检查的未来（Polonius）与运行时验证（Miri、Stacked/Tree Borrows）。

| 资源 | 地址 | 任务 |
|-|-|-|
| [`compiler/rustc_borrowck/src/polonius/`](../../compiler/rustc_borrowck/src/polonius/)（本仓库） | rustc 侧的事实导出层 | 读 `mod.rs`，理解 MIR 事实如何导出 |
