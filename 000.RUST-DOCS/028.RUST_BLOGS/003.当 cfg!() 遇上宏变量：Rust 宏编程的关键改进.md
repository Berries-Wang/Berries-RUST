# 当 cfg!() 遇上宏变量：Rust 宏编程的关键改进

Rust 1.96.0 允许将 `expr` 元变量传递给 `cfg!()`，填补了宏系统与条件编译之间长期存在的缝隙。

## 问题

```rust
macro_rules! platform_fn {
    ($os:expr) => {
        if cfg!($os) {  // 1.96.0 前无法编译
            // Linux-specific implementation
        }
    };
}
```

尽管 `$os:expr` 展开后看起来和手写的 `target_os = "linux"` 一样，宏系统却不认为它能直接喂给 `cfg!()`。

### 根源：两个求值阶段

1. **宏展开阶段**：`macro_rules!` 匹配模式、替换模板、生成 Token 流，`cfg!()` 此时被视为普通宏调用
2. **条件编译阶段**：`cfg!()` 求值，检查目标平台配置

问题在于：第一阶段生成的 `cfg!()` 参数是宏元变量，第二阶段的条件编译逻辑不认识这种变量形式。

### 旧绕过方案

```rust
// 每个平台一个宏分支，组合爆炸
macro_rules! platform_fn {
    (target_os = "linux") => { #[cfg(target_os = "linux")] fn_impl!(); };
    (target_os = "macos")  => { #[cfg(target_os = "macos")]  fn_impl!(); };
}
```

## 1.96.0 改进

让宏展开阶段生成的 `cfg!()` 调用能携带表达式元变量，并在条件编译阶段正确识别和求值。

**之前：** 无法直接将 `$cfg_test` 传给 `cfg!()`

**之后：**

```rust
macro_rules! dispatch {
    ($cfg_test:expr, $true_branch:expr, $false_branch:expr) => {
        if cfg!($cfg_test) {
            $true_branch
        } else {
            $false_branch
        }
    };
}

dispatch!(target_os = "linux", {
    println!("Linux path");
}, {
    println!("Other OS path");
});
```

## 实际场景

### 测试辅助宏

**之前：** 在调用侧用 `#[cfg()]` 做分支

```rust
macro_rules! test_with_features {
    ($name:ident, $body:block) => {
        #[cfg(feature = "nightly")]
        #[test] fn $name() { $body }
        #[cfg(not(feature = "nightly"))]
        #[test] #[ignore] fn $name() { $body }
    };
}
```

**之后：** 配置逻辑收进宏内部

```rust
macro_rules! test_with_features {
    ($name:ident, $cfg_test:expr, $body:block) => {
        #[test]
        fn $name() {
            if cfg!($cfg_test) {
                $body
            } else {
                // skip or fallback
            }
        }
    };
}
```

## 对宏生态的影响

- **条件编译抽象封装**：宏内部用 `cfg!()` 处理传入的平台参数，而非暴露多个宏分支
- **跨 crate 配置传递**：上游配置参数可直接传递给条件编译逻辑
- **宏接口简化**：条件判断完全封装在内部，对外只暴露简洁的参数接口
- **proc macro 受益**：生成的 Token 流中含 `cfg!()` 调用时可更自由地构造参数

## 兼容性

向后兼容，已有代码不受影响。之前不能编译的代码（向 `cfg!()` 传递宏变量）在 1.96.0+ 可正常编译。
