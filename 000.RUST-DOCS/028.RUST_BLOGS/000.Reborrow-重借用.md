# Reborrow 重借用
Rust 的借用检查器能区分 & 和 &mut、能自动在传参时把 &mut T 隐式重借为新的引用，但这一切只对内建引用类型有效。当你定义了一个自定义的引用包装类型——比如 Pin<&T>、Ref<'_, T>、或者自己写的某种「标记引用」——这些自动重借的便利就消失了。正在推进的 Reborrow 和 CoerceShared trait，正是要填补这个缺口。
- Rust 借用检查器（Borrow Checker）中一个非常核心且优雅的机制


## 重借（Reborrow）是什么
```rust
fn main() {
    println!("Hello, world!");
    let mut v = 42;
    let r = &mut v;
    read(r);
    write(r);
    write(r);
}

fn read(x: &i32) -> i32 {
    *x
}

fn write(x: &mut i32) {
    *x += 1;
}
```

这里的关键在于 read(r) 那一行。r 的类型是 &mut i32，而 read 接受 &i32。编译器自动做了两件事：它先对 r 执行了一次重借（reborrow），生成一个 &*r——也就是从 &mut i32 重新借出一个 &i32——然后把这次重借的结果传给 read。由于这次重借只是共享引用，原始的可变引用 r 在 read 返回后仍然可用，所以 write(r) 可以正常编译。
- &*r: 当编译器发现你在对一个引用再次创建引用时，它会触发重借用（Reborrow）机制：
  + 派生关系：新生成的引用（如传给 read 的 &i32）并不是从原始数据 v 独立借出的，而是从 r 派生出来的。
  + 权限让渡：r 暂时将自己的一部分权限（这里是只读权限）“借”给了这个新引用。
  + 生命周期绑定：这个新引用的生命周期被严格限制在 read(r) 这个函数调用的作用域内。

这个机制在 Rust 中叫 重借（reborrow）。它是编译器在 MIR 层面自动插入的隐式 &* 或 &mut * 操作，是让可变引用在多次传参之间「续命」的核心基础。如果没有重借，你就得手动写 read(&*r)，然后在每次传参后手动跟踪引用是否可用——完全违背了 Rust 的零成本抽象承诺。


### 局限
##### 自定义引用类型无法重借
这种自动重借只对内建的 &T 和 &mut T 生效。如果你定义了一个自定义的引用包装类型：
```rust
struct MyRef<'a, T>(&'a T);

fn read(x: &i32) -> i32 { *x }

let v = 42;
let r = MyRef(&v);
// read(r);  // 编译错误：MyRef<i32> 不是 &i32
```

### Reborrow Trait：让重借变得可扩展
```rust
// library/core/src/ops/reborrow.rs
trait Reborrow {
    type Target: ?Sized;
    type Borrowed<'a>: Target = &'a Self::Target
    where
        Self: 'a;
    fn reborrow(&self) -> Self::Borrowed<'_>;
}

trait CoerceShared: Reborrow {
    type Shared: ?Sized + Reborrow;
    fn coerce_shared(&self) -> &Self::Shared;
}
```
Reborrow 描述的是「从一种引用类型重借出另一种引用」的能力。任何实现了 Reborrow 的类型，都可以让编译器知道：当我被传给一个接受引用的函数时，应该自动插入怎样的转换。

CoerceShared 更进一步，处理的是从可变引用（或独有引用）到共享引用的自动转换——类似于当前 &mut T 到 &T 的隐式重借。

有了这两个 trait，自定义引用类型只需要几个 impl 就能获得自动重借能力：
```rust
impl<'a> Reborrow for CustomRef<'a, i32> {
    type Target = i32;
    type Borrowed<'b> = &'b i32 where Self: 'b;
    fn reborrow(&self) -> &i32 { &self.0 }
}
```
然后编译器就知道：当 CustomRef<'a, i32> 被传给一个接受 &i32 的函数时，应该自动调用 reborrow()，而不是报类型不匹配。

##### 从手动 impl 到 derive
当前的 PR 实现还需要手工编写上述 impl，这在实际工程中会非常繁琐。因此项目组也在同步推进 derive 宏的支持。最终目标是让用户这样写：
```rust
#[derive(Reborrow, CoerceShared(CustomRef))]
struct CustomMut<'a, T> { /* ... */ }
```
derive 宏会自动生成从 CustomMut 到 CustomRef 的重借逻辑，以及从 CustomRef 到内部引用的进一步重借。开发者只需要声明「这个类型是一种引用」的意图，编译器负责填充所有转换细节。

##### Q&A

###### 为什么 r 还能继续使用？（权限的“暂停”与“恢复”）
因为传给 read 的引用只是 r 的一个“临时分身”（重借用），它的作用域在 read 函数返回的那一刻就结束了。
- 在 read(r) 执行期间，r 处于被“冻结”或“部分借用”的状态。
- 当 read 返回后，这个临时的 &i32 引用失效，r 重新拿回了完整的可变权限。
- 因此，后续的 write(r) 依然可以合法地获取 r 的可变权限来修改数据。

###### 为什么write(r)能继续使用r？
核心原因在于 Rust 的非词法生命周期（Non-Lexical Lifetimes, NLL）机制以及可变引用的隐式转换。
+ 可变引用可以隐式转换为不可变引用
  - 在 Rust 中，&mut T 可以自动降级（隐式转换）为 &T。因此，当你把可变引用 r 传递给 read(x: &i32) 函数时，Rust 会自动将其转换为不可变引用。
+ 非词法生命周期（NLL）的借用检查
  - 在早期的 Rust 版本中，变量的生命周期是从声明开始，一直到作用域结束。但在现代 Rust 中，引入了 NLL 机制：引用的生命周期仅持续到它最后一次被使用的地方。
+  没有发生“读写冲突”
  - Rust 的借用检查器（Borrow Checker）有一条核心规则：在任意给定时刻，要么只能有一个可变引用，要么只能有多个不可变引用，不能同时存在。
    + ```rust
          fn main() {
              println!("Hello, world!");
              let mut v = 42;
              let r = &mut v;
              read(r);
              write(r);
              let r1 = &*r;
              // 此时编译器就会报错，因为 r1 的生命周期跨越了 write(r)，导致可变借用和不可变借用同时存在，违反了 Rust 的安全规则。
              write(r); // cannot borrow `*r` as mutable because it is also borrowed as immutable mutable borrow occurs here
              println!("{}", r1);
          }
          
          fn read(x: &i32) -> i32 {
              *x
          }
          fn write(x: &mut i32) {
              *x += 1;
          }
      ```
  - 虽然 r 既被用作不可变引用又被用作可变引用，但它们是交替发生的，而不是同时发生的。每次调用 read 时，不可变借用都会及时释放，从而为下一次 write 的可变借用腾出空间。因此，编译器认为这段代码是内存安全的，允许 write(r) 被执行多次。
  

## 总结
即使 Reborrow trait 尚未稳定，理解它的存在也能帮你更好地理解 Rust 引用系统的工作原理：
- Rust 中 &T 和 &mut T 的隐式重借不是魔法，而是编译器硬编码的一套规则。Reborrow trait 的目标是让这套规则变得可扩展。
- 如果你在写自定义的智能指针或引用包装类型，当前应提供显式的 as_ref()、as_mut()、deref() 方法。等 Reborrow trait 稳定后，可以平滑迁移到自动重借。
- 对于 AI 编码工具和代码生成场景，Reborrow trait 的落地意味着生成的代码将更简洁——工具不需要猜测如何拆解自定义引用，编译器会处理这一切。
