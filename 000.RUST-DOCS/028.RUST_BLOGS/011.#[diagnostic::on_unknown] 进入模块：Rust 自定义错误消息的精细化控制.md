# `#[diagnostic::on_unknown]` 进入模块：Rust 自定义错误消息的精细化控制

Rust 编译器的错误信息一直在持续改进。但一个更隐蔽的变化也在同步发生——编译器正在逐渐开放"自定义诊断"的能力，让 crate 作者和库开发者能在特定场景下提供比默认错误更友好的提示。`#[diagnostic::on_unknown]` 从 crate 级别扩展到模块级别，就是这个方向上一个值得关注的动作。

## 诊断属性的进化路径

Rust 的诊断属性（diagnostic attributes）是一组以 `#[diagnostic::...]` 开头的注解，它们不改变程序的行为，只影响编译器如何报告问题。最常见的几个包括：

- `#[diagnostic::on_unimplemented]`：当某个 trait 未实现时，显示自定义的错误消息
- `#[diagnostic::on_unknown_attribute]`：当遇到未知属性时，自定义提示

这些属性的设计理念是：与其让编译器给出通用的错误信息，不如让库作者利用他们对领域的理解，提供更有针对性的诊断。

不过，`#[diagnostic::on_unknown]` 在早期版本中有一个明显的限制——它只能作用在 crate 根级别（通过 `#!` 内部属性），或者逐个标注到具体的 item 上。这意味着如果你有一个包含大量子模块的大型 crate，想要为一个模块内的多个导入点提供自定义诊断，就必须在每个可能出错的位置重复写同样的属性。

## 模块级别支持的突破

最近合并的 PR #157926 改变了这一局面。现在 `#[diagnostic::on_unknown]` 可以直接应用在 `mod` 上，覆盖该模块内所有未解析的导入项。

新的使用方式非常直接：

```rust
#[diagnostic::on_unknown(message = "`{Unresolved}` 不在模块 `{This}` 中")]
pub mod x {
    pub struct Foo;
}

pub use x::Bar; // 这里会触发自定义错误消息
```

当用户错误地尝试从模块 `x` 导入一个不存在的 `Bar` 时，编译器不再输出默认的 `error[E0432]` 消息，而是显示：

```
`Bar` 不在模块 `x` 中
```

这个能力看似简单，但它的价值体现在消息中两个插值变量上：

- `{Unresolved}`：会自动替换为用户试图导入但找不到的具体名称
- `{This}`：会自动替换为当前模块的名称

这意味着一条属性声明就能覆盖模块中所有可能的未解析导入场景，而不需要为每个可能出错的名字单独编写诊断逻辑。

## 内部属性支持

除了外部属性写法，模块内部属性形式也已经支持：

```rust
pub mod y {
    #![diagnostic::on_unknown(message = "not found: `{Unresolved}`")]
    // 模块内的所有未解析导入都会使用这条自定义消息
}
```

需要注意的是，内部属性形式仍然需要 `#![feature(custom_inner_attributes)]` 特性门控，因为它本质上属于自定义内部属性机制的一部分。

## 三个最有价值的应用场景

### 1. 大型符号表的友好提示

Clippy 编译器 lint 集合内部维护了一个庞大的符号表（`rustc_span` 的 `sym` 模块），其中包含了 Rust 编译器能够识别的各种符号名。当开发者拼写错误时，之前只能看到含糊的"未找到"错误。现在只需在 `sym` 模块上放置一条 `#[diagnostic::on_unknown]`，就能让错误的符号引用给出更明确的提示，甚至可以直接建议正确的符号名。

### 2. 改名或废弃的标识符墓碑

当库中某个公共项被重命名或废弃时，通常的做法是保留旧名称并用 `#[deprecated]` 标记。但有些情况下旧名称被完全移除时，用户只会看到"未找到"的错误，不知道这个名称曾经存在过、以及应该用什么替代。通过模块级别的诊断属性，可以为整个模块设置墓碑消息：

```rust
#[diagnostic::on_unknown(message = "`{Unresolved}` 已经移除了，请参考迁移指南")]
pub mod legacy {
    // 旧的公共 API 已经全部迁移到其他地方
}
```

### 3. 宏生成的复杂模块结构

在宏密集的代码库中，生成的模块结构可能非常复杂，用户很容易在查阅生成的代码时混淆导入路径。模块级别的诊断属性允许为整个宏生成区域统一设置错误提示，降低调试宏生成代码的认知负担。

## 编译器团队的设计权衡

这项改动在今年 6 月合并时，也引发了关于诊断属性扩展方向的讨论。审查者提出过一个值得关注的顾虑：如果允许用户自定义所有诊断消息，编译器会不会因此背上沉重的维护负担？每一次内部重构都可能需要更新这些自定义消息的解析逻辑。

而实现者的回应也很务实：自定义诊断属性实际上也为编译器省掉了一部分错误报告代码——当用户提供了自定义消息时，编译器就不再需要为这些特定的错误场景生成通用提示文本。这是一个双向的简化。

最终，该改动以"不稳定"状态被合并，目标是 Rust 1.98.0。这意味着 `diagnostic::on_unknown` 属性本身仍然是可变的，未来可能会根据实际使用反馈进行调整。

## 对开发者的意义

对于普通 Rust 使用者，这个特性不会直接改变日常编码体验——你看到的错误信息仍然是编译器生成的，只不过在使用了该特性的 crate 中，这些消息会更有针对性。

但对于 crate 作者和库维护者来说，这是一个值得关注的工具。它让"改善用户体验"这件事不再局限于文档和注释，而是可以直接深入到编译器的诊断流程中。特别是在以下场景中，投入一点配置时间就能显著降低用户的使用摩擦：

- 提供多语言的 crate 错误提示
- 为特定领域（DSL）或深度嵌套的模块结构设置上下文感知的诊断
- 在库的大版本升级期间，作为迁移辅助手段

当前该特性仍处于 **unstable** 阶段，需要在 nightly 工具链下通过 `#![feature(diagnostic_on_unknown)]` 启用。对于已经在使用 nightly 并关注 API 体验的库开发者来说，现在就可以开始尝试这个能力，为稳定后的正式采用做好准备。
