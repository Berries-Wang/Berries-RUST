# cfg_select! 宏：Rust 条件编译的工具链升级

> Rust 1.95.0 在 2026 年 4 月发布时，引入了一个新的宏：`cfg_select!`。它的功能很简单——在编译期根据目标平台配置选择不同的代码分支。但这件事如果只被当作"官方版 cfg-if"来理解，就低估了它背后的信号。

## 条件编译的一个缺口

Rust 的条件编译机制一直有两套工具。一套是属性式的：在声明前标注 `#[cfg(target_os = "linux")]`，控制某个函数、模块或整个声明是否参与编译。另一套是函数式的：`cfg!(target_os = "linux")` 返回一个编译期布尔值，用于运行时分支。

这两套工具的中间地带始终是空缺的：如果你想做"根据不同平台选择不同实现"，而不是简单的"有或没有"，怎么写？

社区的回答是 **cfg-if crate**。这个由 Alex Crichton 写的 crate 几乎是 Rust 生态中最简单的包——它只提供一个 `cfg_if!` 宏，把一系列 `cfg()` 谓词映射到不同的代码块。尽管功能单一，它却出现在成千上万 crate 的依赖树里。从 libc、rand 到 tokio、serde，任何需要跨平台的 Rust 项目几乎都会引入它。

在 2025 年底到 2026 年初，cfg-if 在 crates.io 上的累计下载量已经超过 **1.3 亿次**。它是 Rust 生态中"隐形的基础设施"——几乎没人专门讨论它，但所有人都在用它。

所以当 Rust 1.95 在标准库中直接提供了 `cfg_select!`，它解决的并不仅仅是"个别名问题"。

## cfg_select! 的用法

`cfg_select!` 的语法看起来很像在 cfg 谓词上做模式匹配：

```rust
cfg_select! {
    target_os = "linux" => {
        fn get_path() -> &'static str { "/etc/config.toml" }
    },
    target_os = "macos" => {
        fn get_path() -> &'static str { "/Library/Application Support/config.toml" }
    },
    _ => {
        fn get_path() -> &'static str { "/etc/config.toml" }
    },
}
```

它与 `cfg!()` 的区别在于：`cfg!()` 返回布尔值，你仍然需要在运行时分发；而 `cfg_select!` 在编译期就完成了选择和展开，未选中的分支根本不会进入编译器的视野。在跨平台项目里，这意味着你可以在不同目标上用完全不同的类型或函数签名，而不仅仅是不同的值。

### 与 cfg-if 的区别

它和 cfg-if 的版本在语义上等价，但有几个微妙之处：

**第一个是卫生性**。cfg-if 作为外部 crate，其宏展开时需要注意标识符冲突问题，而 `cfg_select!` 作为标准库内置宏，与编译器的集成更深，在卫生性上更可靠。

**第二个是求值时机**。`cfg_select!` 是编译期第一公民，它在抽象语法树层面被处理，而不是通过宏展开后的条件判断。这意味着它可以出现在更多位置——比如作为表达式的一部分直接参与值计算：

```rust
let parallelism = cfg_select! {
    target_os = "linux" => num_cpus::get(),
    target_os = "windows" => 1,
    _ => num_cpus::get().max(1),
};
```

**第三个也是最重要的**：它让 Rust 项目少了一个对 cfg-if 的隐式依赖。

## 依赖树里的"灰尘"

cfg-if 虽然只有几十行代码，但它有两个问题不是代码量能衡量的。

**第一个是版本碎片**。cfg-if 经历了 1.0 到 1.3 的迭代。在复杂的依赖图中，同一个项目可能因为不同传递依赖锁定了不同版本——A 包依赖 cfg-if 0.1，B 包依赖 cfg-if 1.0，但编译器不会报版本冲突，只会生成两份几乎相同的代码。这对二进制体积和编译时间都是一种隐性浪费。

**第二个是审计面**。对于注重供应链安全的团队，每次 cargo audit 扫描出来的"脊椎"里，cfg-if 都是一个额外的审计项——哪怕它的代码足够简单，简单到不需要审计。

`cfg_select!` 在标准库中内置后，新建的项目完全不需要将 cfg-if 加入依赖。存量项目也可以逐步迁移。标准库的特性——不引入额外依赖、不产生版本碎片、不需要通过 cargo 解析——在这里体现得很直接。

这并不是说 cfg-if 会立刻消失，它依然会长期存在于众多旧版本的依赖树中。但 Rust 编译器团队在"可选"还是"内置"之间选择后者的决策，传递了一个清晰的信号。

## 吸收社区 crate：一条隐形的 roadmap

`cfg_if! → cfg_select!` 并不是孤例。Rust 的标准库一直在系统性地吸收社区 crate 中经过验证的能力：

- `lazy_static` 和 `once_cell` 的能力被 `LazyLock` 和 `OnceLock` 覆盖
- `cfg-if` 的生态位被 `cfg_select!` 接管
- `regex` 虽然还没进标准库，但 `std::path` 和其他模块已经在内置了对常见模式的原生支持

这种"吸收"的节奏正在加快。一个关键的变化是，Rust 项目开始为这些内置宏提供更干净的接口，而不是简单地把社区 crate 的 API 平移进来。`cfg_select!` 的语法和语义都经过了重新设计，而不是照搬 cfg-if 的拼写。

对于团队来说，这意味着在评估依赖时可以有一个判断标准：如果某个功能已经被标准库覆盖，是否还要保留外部依赖？在多数情况下，"不用加依赖"是一个足够有力的理由。

## 跨平台的工程选择

有了 `cfg_select!`，跨平台代码的组织方式也有了一些微妙的变化。

以前，如果你需要在 Linux 和 macOS 上使用不同的系统调用，常见的写法是在代码中先写一个 `cfg!(target_os = "...")` 并在运行时做分发，或者把不同平台的实现拆到不同的文件里，用 `#[cfg(...)]` 控制模块的编译。

`cfg_select!` 提供了一种中间的粒度：同一函数内的平台分块。上面的 `get_path()` 例子中，三个平台的实现在同一个函数体内，但只有匹配平台的那个分支被实际编译。这对于平台差异代码的维护者来说是一种好的模式——差异集中在一个地方，而不是分散在不同文件中。

在代码审查的场景中，这种集中式的写法也更容易发现问题。评审者不需要在不同文件间跳转来对比平台差异。

## 迁移路径

从 cfg-if 迁移到 `cfg_select!` 并不复杂。核心变化是语法：

```rust
// 之前 (cfg-if)
cfg_if::cfg_if! {
    if #[cfg(target_os = "linux")] {
        // ...
    } else if #[cfg(target_os = "macos")] {
        // ...
    } else {
        // ...
    }
}

// 之后 (cfg_select!)
cfg_select! {
    target_os = "linux" => {
        // ...
    },
    target_os = "macos" => {
        // ...
    },
    _ => {
        // ...
    },
}
```

从 Rust 1.95 起，在新建的 crate 中可以直接使用 `std::cfg_select!`（它已经被 `std::prelude` 导出，可以直接写 `cfg_select!`）。对于仍需要支持旧版本 Rust 的项目，可以在依赖中保留 cfg-if，同时在新代码中逐步采用 `cfg_select!`，并在 MSRV 提升后移除 cfg-if。

> 值得注意的是，`cfg_select!` 暂时还不支持所有 `cfg()` 谓词的复杂组合。对于多条件谓词（如 `all(target_os = "linux", target_arch = "x86_64")`），建议先使用逐级嵌套或保留 cfg-if。这个限制随着编译器版本的更新可能会逐步放开。

## 标准化的真正价值

替换一个下载量 2 亿的 crate，自然有减少依赖的意义。但 `cfg_select!` 进入标准库的价值远不止于此。

**第一，编译时间的稳定性。** 外部 crate 在 CI 中是需要额外拉取和构建的。对 CI 管线而言，每减少一个需要下载的依赖，构建的确定性就提高一分。cfg_if 本身很小，但它的缺失会导致整个构建失败——标准库中的 `cfg_select!` 不存在这个问题。

**第二，新项目的默认选择。** 当一个功能进入标准库，它就成为新项目零成本的起点。你不会再犹豫"要不要引入 cfg-if 来做平台分派"——直接用 `cfg_select!`，无需 `Cargo.toml` 改动，无需拉依赖，无需阅读第三方 crate 文档。

**第三，语言层面的语义统一。** 条件编译的未来扩展——比如条件组合、嵌套模式、更复杂的求值策略——如果基于标准库的 `cfg_select!` 来设计，语言委员会就不需要兼顾第三方 crate 的历史包袱。这是 Rust 社区经常讨论的"标准库先行"模式的一个典型案例。

## 同一版本中的其他编译时改进

Rust 1.95 不只有 `cfg_select!`。同版本稳定的 **if-let 守卫（if-let guards in match expressions）** 是另一个值得关注的编译时表达能力提升。

它允许在 match 分支的 guard 中做模式匹配：

```rust
match value {
    Some(x) if let Ok(y) = compute(x) => {
        println!("x = {}, y = {}", x, y);
    }
    _ => {}
}
```

这是 Rust 1.88 中 let-chains 的自然延续。let-chains 让 if 语句可以串联多个 let 绑定；if-let 守卫则把这个能力带到了 match 分支里。对于那些需要在匹配成功后再做一次校验或转换的场景，这比嵌套 match 要简洁得多。

再配合 `cfg_select!`，Rust 1.95 传递了一个清晰的信号：**编译时的表达能力正在成为语言演进的主线之一**。

## 迁移建议

如果你现在正在用 cfg-if，是否应该立刻切到 `cfg_select!`？

建议分两步考虑：

1. **新代码直接使用 `cfg_select!`。** 标准库自带，零成本引入。语法也足够直观，团队成员可以快速上手。
2. **存量项目不必着急。** cfg_if 仍然在正常维护，不会因为 `cfg_select!` 的稳定而停止工作。但可以在技术债清理或大版本更新时顺手替换，把依赖列表缩短一项。

对于库作者来说，如果你的 crate 依赖 cfg-if 只是为了内部的条件编译，从下一版开始迁移到 `cfg_select!` 是一个低风险、高收益的改进。唯一的兼容性注意点是：`cfg_select!` 在 Rust 1.95 之前不可用，如果你的 crate 还支持更老的工具链版本，需要保留 cfg-if 作为降级方案，或者提升 MSRV 到 1.95。

## 不止是宏

`cfg_select!` 本身只是一个宏。但它背后折射出的，是 Rust 的成熟方式。

语言发展的常见路径有两种：一种是激进地往语法层面塞新特性，另一种是逐步将生态中验证过的模式吸收到标准库。Rust 显然选择了后者。cfg-if 到 `cfg_select!` 的迁移，与此前 `lazy_static` 到 `LazyLock`、`once_cell` 到标准库 `OnceLock` 的路径一致：**让社区先行探索，筛选出最优方案，再标准化**。

这种模式的好处是风险可控、方向明确。缺点可能是慢。但对于一门以稳定性为核心承诺的系统语言来说，慢就是稳。

下一次你打开 `Cargo.toml` 时，不妨扫一眼 cfg-if 是否还躺在依赖列表里。如果还在，Rust 1.95 给了你一个优雅的退出理由。

# cfg_select! 高级实战：构建零开销的跨平台抽象层

> 适用场景：多架构微服务、嵌入式固件、条件编译复杂库
> 核心目标：以编译期决策替代运行时分支，实现类型安全、零成本的平台抽象

## 一、原理深度解析：编译期求值机制

### 1.1 宏展开本质

`cfg_select!` 并非运行时 match，而是编译期条件展开器。其工作流程：

```rust
// 源码
cfg_select! {
    target_os = "linux" => "linux",
    target_os = "macos" => "macos",
    _ => "unknown",
}

// 编译期展开（以 Linux 目标为例）
"linux"  // 其他分支被完全剔除，零二进制体积占用
```

### 1.2 与 cfg-if 的关键差异

| 维度 | cfg-if (crate) | cfg_select! (原生) |
|------|----------------|---------------------|
| 依赖管理 | 外部依赖，需版本锁定 | 零依赖，语言原生 |
| 展开粒度 | 语句级（需 `{}` 包裹） | 表达式级（可直接返回值） |
| 类型推导 | 需手动保证分支类型一致 | 编译器自动推导，类型错误编译期捕获 |
| 嵌套支持 | 嵌套时缩进层级深 | 支持扁平化多条件组合 |

## 二、高级用法模式库

### 2.1 表达式模式：编译期字符串/数值选择

```rust
// 场景：多环境配置注入
pub const API_ENDPOINT: &str = cfg_select! {
    feature = "prod" => "https://api.prod.example.com",
    feature = "staging" => "https://api.staging.example.com",
    target_os = "windows" => "http://localhost:8080", // 开发默认
    _ => "http://127.0.0.1:8080",
};

// 场景：平台特定常量
pub const MAX_CONNECTIONS: usize = cfg_select! {
    target_pointer_width = "64" => 10_000,
    target_pointer_width = "32" => 1_000,  // 内存受限平台降级
    _ => 500,
};
```

### 2.2 函数/类型定义模式：平台特化实现

```rust
// 场景：加密后端抽象
cfg_select! {
    all(target_arch = "x86_64", target_feature = "aes") => {
        #[inline(always)]
        pub fn encrypt_aesni(data: &[u8], key: &[u8; 16]) -> Vec<u8> {
            // 使用 AES-NI 指令集加速
            unsafe { aesni_encrypt_intrinsics(data, key) }
        }
    }
    target_family = "unix" => {
        pub fn encrypt_aesni(data: &[u8], key: &[u8; 16]) -> Vec<u8> {
            // Unix 回退：OpenSSL 绑定
            openssl_encrypt(data, key)
        }
    }
    _ => {
        pub fn encrypt_aesni(data: &[u8], key: &[u8; 16]) -> Vec<u8> {
            // 纯 Rust 实现：兼容性优先
            soft_aes_encrypt(data, key)
        }
    }
}
```

### 2.3 组合条件模式：精细平台匹配


### 3.2 平台抽象层实现（src/platform/mod.rs）

```rust
//! 零成本平台抽象：编译期选择，运行时零分支

// 网络后端选择
cfg_select! {
    all(target_os = "linux", feature = "io_uring") => {
        pub(crate) use self::linux_uring as backend;
        pub const PLATFORM_TAG: &str = "linux-uring";
    }
    target_family = "unix" => {
        pub(crate) use self::unix_epoll as backend;
        pub const PLATFORM_TAG: &str = "unix-epoll";
    }
    target_os = "windows" => {
        pub(crate) use self::windows_iocp as backend;
        pub const PLATFORM_TAG: &str = "windows-iocp";
    }
    target_arch = "wasm32" => {
        pub(crate) use self::wasm_fetch as backend;
        pub const PLATFORM_TAG: &str = "wasm-fetch";
    }
    _ => {
        pub(crate) use self::fallback as backend;
        pub const PLATFORM_TAG: &str = "fallback";
    }
}

// 统一接口：业务代码仅依赖此 trait
pub trait NetworkBackend {
    async fn connect(&self, addr: &str) -> std::io::Result<Connection>;
    fn platform_tag(&self) -> &str { PLATFORM_TAG }
}

// 条件编译模块声明
cfg_select! {
    all(target_os = "linux", feature = "io_uring") => {
        mod linux_uring;
    }
    target_family = "unix" => {
        mod unix_epoll;
    }
    target_os = "windows" => {
        mod windows_iocp;
    }
    target_arch = "wasm32" => {
        mod wasm_fetch;
    }
    _ => {
        mod fallback;
    }
}
```

### 3.4 自动化交叉构建脚本（scripts/cross-build.sh）

```bash
#!/usr/bin/env bash
set -euo pipefail

TARGETS=(
    "x86_64-unknown-linux-gnu"
    "aarch64-unknown-linux-musl"   # ARM64 Linux (容器/嵌入式)
    "x86_64-pc-windows-gnu"        # Windows (MinGW)
    "wasm32-unknown-unknown"       # WASM (边缘计算)
)

for target in "${TARGETS[@]}"; do
    echo "Building for $target..."

    cargo build \
        --release \
        --target "$target" \
        $( [[ "$target" == *"linux"* ]] && echo "--features io_uring" || true ) \
        $( [[ "$target" == "wasm32"* ]] && echo "--no-default-features" || true )

    # 验证二进制元数据
    if [[ "$target" != "wasm32"* ]]; then
        file "target/$target/release/service-gateway" | grep -q "ELF\|PE" || {
            echo "Binary validation failed for $target"
            exit 1
        }
    fi
done

echo "Multi-arch build completed"
```

## 四、性能优化：编译期决策的极致利用

### 4.1 避免运行时分支的基准测试

```rust
// benches/cfg_select_bench.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn runtime_match_approach(platform: &str) -> usize {
    // ❌ 运行时分支：每次调用都需判断
    match platform {
        "linux" => 10_000,
        "macos" => 8_000,
        "windows" => 5_000,
        _ => 1_000,
    }
}

fn cfg_select_approach() -> usize {
    // ✅ 编译期决策：零运行时开销
    cfg_select! {
        target_os = "linux" => 10_000,
        target_os = "macos" => 8_000,
        target_os = "windows" => 5_000,
        _ => 1_000,
    }
}

fn bench_runtime(c: &mut Criterion) {
    c.bench_function("runtime_match", |b| {
        b.iter(|| runtime_match_approach(black_box("linux")))
    });
}

fn bench_compile_time(c: &mut Criterion) {
    c.bench_function("cfg_select", |b| {
        b.iter(|| cfg_select_approach()) // 编译器优化为常量
    });
}

criterion_group!(benches, bench_runtime, bench_compile_time);
criterion_main!(benches);
```

典型结果（x86_64 Linux, --release）：

## 五、迁移策略：从 cfg-if 平滑过渡

### 5.1 自动化重构脚本（scripts/migrate-cfg-if.py）

```python
#!/usr/bin/env python3
"""
将 cfg-if! 调用转换为原生 cfg_select!
支持语句级与表达式级模式
"""
import re
import sys
from pathlib import Path

CFG_IF_PATTERN = re.compile(
    r'cfg_if!\s*\{(?:\s*if\s+#\[cfg\((?P<cond>[^)]+)\)\]\s*\{(?P<then>.*?)\})+'
    r'(?:\s*else\s*\{(?P<else_>.*?)\})?\s*\}',
    re.DOTALL
)

def convert_cfg_if(match: re.Match) -> str:
    cond = match.group('cond')
    then = match.group('then').strip()
    else_ = match.group('else_').strip() if match.group('else_') else '{}'
    return f'cfg_select! {{\n    {cond} => {{ {then} }},\n    _ => {{ {else_} }}\n}}'

def migrate_file(filepath: Path) -> int:
    content = filepath.read_text(encoding='utf-8')
    new_content, count = CFG_IF_PATTERN.subn(convert_cfg_if, content)
    if count > 0:
        new_content = re.sub(r'use\s+cfg_if::cfg_if;\s*', '', new_content)
        filepath.write_text(new_content, encoding='utf-8')
        print(f"✓ {filepath}: {count} conversion(s)")
    return count

if __name__ == '__main__':
    root = Path(sys.argv[1]) if len(sys.argv) > 1 else Path('.')
    total = sum(migrate_file(f) for f in root.rglob('*.rs'))
    print(f"Migrated {total} cfg_if! invocation(s)")
```

`cfg_select!` 的终极价值，不在于"替代 cfg-if"，而在于将平台差异的复杂性锁定在编译期：

- **业务代码零感知**：核心逻辑无需 `#[cfg]` 污染，专注领域建模

- **类型安全前置**：平台特化实现的接口一致性由编译器保障
- **供应链更纯净**：减少外部依赖，降低维护成本与安全风险

# cfg_select! 稳定了：cfg-if 近十亿次下载的使命，编译器自己接

Rust 1.95.0 正式稳定了 `cfg_select!` 宏——一个编译器内置的条件编译多分支选择机制。从此，Rust 项目处理平台分支、特性门控等编译期选择时，不再依赖外部 crate，语言本身就能完成这件事。

这不是一个小改动。cfg-if 是 Rust 生态中下载量接近十亿、反向依赖超过 2600 个 crate 的基础设施级库。标准库内部也在用它。如今，编译器原生替代方案的到来，意味着一条从 2015 年就开始的路径终于闭环。

## 问题：cfg-if 做了什么，以及它做不到什么

几乎所有需要跨平台支持的 Rust 项目都见过这段代码：

```rust
cfg_if::cfg_if! {
    if #[cfg(target_os = "linux")] {
        fn platform_name() -> &'static str { "linux" }
    } else if #[cfg(target_os = "macos")] {
        fn platform_name() -> &'static str { "macos" }
    } else if #[cfg(target_os = "windows")] {
        fn platform_name() -> &'static str { "windows" }
    } else {
        fn platform_name() -> &'static str { "unknown" }
    }
}
```

`cfg_if!` 用 if / else if / else 的写法串联多个 `#[cfg]` 条件，每个分支互斥展开。这解决了 `#[cfg]` 属性叠加时条件组合不直观的问题——手写 `#[cfg(all(target_pointer_width = "64", not(unix)))]` 谁都觉得别扭。

但 `cfg_if!` 有几个结构性缺陷：

**只能在项位置使用。** 它无法用在表达式里。想根据编译配置给一个变量赋不同值，要么拆成多个 const/static 定义，要么退回 `cfg!()` 加 if-else 的组合——后者在编译期依然会检查所有分支的类型一致性，等于把不该存在的代码路径也拉进了类型检查。

**不匹配时静默消失。** 如果所有 if 和 else if 的条件都不满足，且没有写 else 分支，`cfg_if!` 展开后什么都不生成。没有编译错误，没有警告。这对调试来说是个坑——你以为分支覆盖了所有情况，实际编译时某个条件没命中，对应代码就凭空消失了。

**展开方式笨重。** `cfg_if!` 的实现依赖 `macro_rules!`，为了让各分支互斥，它在展开时把前面所有条件取反叠加到后面的分支上。三个分支就能产生 `#[cfg(not(any(A, B)))]` 这样的复合条件，读起来费劲，维护起来更费劲。

**语法不直观。** `if #[cfg(X)]` 把 Rust 的 match 语义和 `#[cfg]` 属性语法混在一起，既不像 match 又不像 if，是一种专为这个宏创造的混合写法。

## cfg_select! 的设计：编译器原生 match，不再靠宏拼装

`cfg_select!` 用的是 Rust 程序员最熟悉的 match 语义——从上到下逐个评估，第一个命中就展开，其余丢弃：

```rust
cfg_select! {
    target_os = "linux" => {
        fn platform_name() -> &'static str { "linux" }
    }
    target_os = "macos" => {
        fn platform_name() -> &'static str { "macos" }
    }
    target_os = "windows" => {
        fn platform_name() -> &'static str { "windows" }
    }
    _ => {
        fn platform_name() -> &'static str { "unknown" }
    }
}
```

对比之下，逻辑一目了然：左边是 cfg 谓词，右边是展开内容，`_` 是兜底。不需要 if，不需要 `#[cfg]` 属性嵌套，不需要在脑子里模拟条件取反。

但真正拉开差距的是三个能力：

### 表达式位置支持

```rust
let os_str = cfg_select! {
    unix => "unix-like",
    windows => "windows",
    _ => "unknown"
};
```

这是 `cfg_if!` 做不到的事。现在条件编译的选择结果可以直接用在赋值、函数参数、返回值等表达式位置，不需要绕路定义常量再引用。未选中的分支在编译期直接丢弃，不参与类型检查——这意味着不同分支甚至可以返回不同类型（只要选中的那个类型满足上下文要求）。

### 不匹配时编译报错

如果没有任何谓词命中，且没有写 `_` 兜底分支，`cfg_select!` 会在编译期触发 `compile_error!`。这比 `cfg_if!` 的静默消失要安全得多——你漏写了某个平台的处理，编译器会直接告诉你，而不是悄悄把那段代码抹掉。

### 专用的不可达谓词警告

Rust 1.95 同时引入了 `unreachable_cfg_select_predicates` lint。如果你写了这样的代码：

```rust
cfg_select! {
    unix => { /* ... */ }
    target_os = "linux" => { /* ... */ }
    _ => { /* ... */ }
}
```

在 Linux 上编译时，unix 命中后 `target_os = "linux"` 永远不会被评估。lint 会捕捉到这种逻辑冗余并发出警告。这相当于编译器帮你审查了条件分支的覆盖率——不是事后静态分析，而是编译期的实时检查。

## 为什么这件事值得关注

### 依赖清理的实际收益

cfg-if 是一个几乎零逻辑的宏——全部实现不到 50 行。但它作为外部依赖，依然要占用 `Cargo.toml` 一行、`Cargo.lock` 一个条目、编译期一次 crate 解析。对于大型 workspace 或嵌入式场景，每个依赖都是编译时间和供应链审查的增量成本。

迁移到 `cfg_select!` 后，这些开销归零。标准库自身已经完成了这个迁移——2025 年 8 月，std 内部所有 `cfg_if!` 用法被替换为 `cfg_select!`，证明了大规模迁移的可行性。

### 从宏拼装到语言语义

`cfg_if!` 是一个 `macro_rules!` 宏，它的展开逻辑是文本级的条件取反拼接。`cfg_select!` 是编译器内置宏，展开时编译器直接知道哪个分支命中，不需要生成一堆 `#[cfg(not(...))]` 的组合属性。

这意味着几个实际好处：

- **展开结果更干净。** 不会出现嵌套五层的 `all(not(A), not(B), not(C))` 条件。
- **诊断信息更准确。** 编译器报错时指向的是你写的谓词，而不是展开后的复合属性。
- **未选中分支不参与解析。** `cfg_if!` 的所有分支都会被 `macro_rules!` 解析一遍；`cfg_select!` 只解析命中的分支——其余部分可以是任意 token 序列，不要求语法合法。这对包含复杂平台特定代码的项目来说，意味着更少的误报和更快的编译。

### 迁移路径清晰

从 `cfg_if!` 迁移到 `cfg_select!` 的模式非常机械：

| cfg-if 写法 | cfg_select! 写法 |
|-------------|------------------|
| `if #[cfg(X)] { ... }` | `X => { ... }` |
| `} else if #[cfg(Y)] { ... }` | `Y => { ... }` |
| `} else { ... }` | `_ => { ... }` |

标准库迁移时甚至用了一条 vim 正则批量完成替换。对于大多数项目，迁移可以一次性做完，不需要逐个分支手动调整。

## 还需要注意的几个边界

**rustfmt 支持尚未实现。** `cfg_select!` 的格式化规则已经由风格团队确定，但 rustfmt 的实现还在进行中。迁移后你可能需要手动调整缩进和对齐。

**外层属性暂不支持。** 目前 `cfg_select!` 的分支上不能写 `#[...]` 外层属性。如果你的 `cfg_if!` 分支里有属性标注，需要把属性移到分支内部的具体项上。

**doc_auto_cfg 的交互已修复。** 早期版本中，`cfg_select!` 内的项不会在文档中显示平台条件标签。这个问题在稳定前已通过"逐项 splatting `#[cfg]`"的方式解决——现在 `cfg_select!` 内的每个项都会正确携带 cfg 信息出现在文档里。

## 实际迁移建议

如果你的项目 MSRV 已经可以升到 1.95，迁移步骤如下：

1. 从 `Cargo.toml` 移除 cfg-if 依赖。
2. 全局搜索 `cfg_if::cfg_if!` 和 `cfg_if!`，替换为 `cfg_select!`。
3. 把 `if #[cfg(PRED)]` 改为 `PRED =>`，把 `else if #[cfg(PRED)]` 改为 `PRED =>`，把 `else` 改为 `_ =>`。
4. 检查是否有在表达式位置使用条件编译的代码，用 `cfg_select!` 的表达式语法简化。
5. 编译并检查 `unreachable_cfg_select_predicates` 警告——它会帮你发现冗余分支。

如果你的项目 MSRV 低于 1.95 且暂时不能升级，cfg-if 会继续正常工作。两者在语义上是兼容的——迁移只是可选的改进，不是强制要求。

## 结语

`cfg_select!` 的稳定，是 Rust 编译器持续将生态中高频使用的外部模式吸收为语言原生能力的一个典型案例。从 `?` 操作符替代 `try!` 宏，到 `async/await` 替代手写 Future 组合子，再到如今 `cfg_select!` 替代 `cfg_if!`——Rust 的演进路线始终在把"开发者不得不靠外部工具弥补的语言短板"逐一收回编译器。

对于 Rust 开发者来说，这件事的直接收益是少一个依赖、多一种表达式位置的条件编译能力、以及编译期对分支覆盖的主动检查。长远看，它标志着条件编译从"宏拼装"阶段正式进入"语言语义"阶段——这和 Rust 其他领域的演进方向是一致的。
