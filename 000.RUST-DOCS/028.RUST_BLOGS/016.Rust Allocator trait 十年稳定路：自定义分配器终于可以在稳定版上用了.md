# Rust Allocator trait 十年稳定路：自定义分配器终于可以在稳定版上用了

如果你写过 Rust，一定用过 `Box::new()` 和 `Vec::new()`。这两个 API 背后的分配器选择，从 Rust 1.0 开始就被固定为全局分配器——你没法在 stable Rust 上让一个 `Box` 使用竞技场分配器，也没法让某个 `Vec` 使用页对齐的内存池。这个限制持续了近十年。

2026 年 5 月，`Allocator` trait 的稳定化 PR 正式提交。这可能是自 `#[global_allocator]` 在 Rust 1.28 稳定以来，标准库分配器 API 最大的一次演进。

## 问题：为什么需要 Allocator trait

Rust 的内存分配能力其实分两层。

**第一层**是 2018 年在 Rust 1.28 稳定的 `#[global_allocator]` 和 `GlobalAlloc` trait。它允许你替换整个程序的全局分配器——从 jemalloc 换成 mimalloc，或者接入自己实现的分配器。但它的粒度是整个程序：所有 `Box`、`Vec`、`HashMap` 的分配都走同一个分配器。

**第二层**就是 `Allocator` trait，从 2016 年的 RFC 1398 开始跟踪，始终停留在 nightly。它允许每个容器独立选择分配器：`Vec<T, MyAlloc>` 而不是 `Vec<T>`。这种"每容器分配器"的能力在游戏引擎（帧分配器）、嵌入式系统（静态内存池）、实时音频（无锁分配器）、WebAssembly（线性内存管理）等场景中是刚需。

这十年间，Rust 项目只能通过两种方式绕过这个限制：要么用 nightly 的 `allocator_api` 特性，要么在每个容器外面包一层自定义的 alloc/dealloc 调用。前者无法在 stable 上使用，后者丢失了类型安全。

## 稳定了什么

这次 PR 稳定的是一个"最小可行"版本：

- `Allocator` trait 本身：包含 `allocate`、`deallocate`、`grow`、`shrink` 等核心方法，以及带默认实现的 `allocate_zeroed`、`grow_zeroed`、`by_ref`
- `Box::new_in()` 和 `Vec::new_in()`：允许传入自定义分配器的构造方法
- `Global` 类型：实现 `Allocator`，包装当前 `#[global_allocator]`，让已有代码可以平滑过渡
- `System` 分配器：作为标准实现提供
- `Allocator for T: GlobalAlloc` 的 blanket impl：所有现有的 `GlobalAlloc` 实现自动获得 `Allocator` 实现

而以下内容这次没有稳定：

- `Allocator` 暂时是 dyn-incompatible 的，不能写成 `Box<dyn Allocator>`
- 只有 `Box` 和 `Vec` 获得了 `new_in` 方法，**`HashMap`、`String`、`Rc`、`Arc` 等容器暂不支持**自定义分配器
- 没有稳定 `allocator_api` 中的高级功能（如 `Allocator` 作为 trait object、`MakeAllocator`、嵌套分配器等）

这种保守策略来自 2026 年 All Hands 上 libs team 和生态利益相关方的共识：当前设计可以在未来向后兼容地扩展，先稳定一个能用的内核，再逐步放开。

## Allocator trait 的核心设计

`Allocator` trait 的设计与 `GlobalAlloc` 有本质区别。

`GlobalAlloc` 是一个 unsafe trait，方法的第一个参数是 `&self`，操作的是裸指针 `*mut u8`。它的调用者需要自己处理 `Layout` 的合法性、内存对齐、零大小分配等细节。

`Allocator` 在安全性上做了显著提升：

- 返回值使用 `Result<NonNull<[u8]>, AllocError>`，而不是返回可能为 null 的裸指针
- 零大小分配被显式支持——实现者不需要处理"分配 0 字节返回 null"的边缘情况
- `grow` 和 `shrink` 有明确的 safety 条件，且在默认实现中做了 `debug_assert`
- soundness 约束经过了 `@RalfJung` 的审查，比最初版本更严格

一个自定义分配器的最小实现只需要两个方法：

```rust
use core::alloc::{Allocator, AllocError, Layout};
use core::ptr::NonNull;

struct Arena;

unsafe impl Allocator for Arena {
    fn allocate(&self, layout: Layout) -> Result<NonNull<[u8]>, AllocError> {
        // 竞技场分配逻辑
        todo!()
    }

    unsafe fn deallocate(&self, ptr: NonNull<u8>, layout: Layout) {
        // 竞技场释放逻辑（可能为空操作）
    }
}

let mut arena_vec: Vec<i32, &Arena> = Vec::new_in(&Arena);
arena_vec.push(42);
```

注意这里的 `Vec<i32, &Arena>`——分配器类型是引用，这意味着分配器本身的生命周期由借用检查器管理。这也是 `Allocator` 的 blanket impl 为 `&A where A: Allocator` 提供实现的原因。

## 对开发者的意义

这次稳定化最大的受益者不是日常写 CRUD 应用的开发者，而是那些对内存布局有精确控制要求的领域。

**游戏引擎：** 可以在帧开始时创建一个线性竞技场，帧内所有临时分配都从这个竞技场分配，帧结束时一次性重置。这种模式在 Unity 的 Burst Compiler、Unreal Engine 的自定义分配器中广泛使用。

**嵌入式系统：** 可以为不同的任务分配不同的静态内存池，避免全局堆的碎片化问题，同时保证最坏情况下的内存可用性。

**实时音频：** 音频回调线程中不能使用锁，也不能调用可能触发页面错误的系统分配器。自定义的无锁分配器可以保证音频线程的确定性延迟。

**WebAssembly：** Wasm 模块的线性内存模型与传统的系统分配器不匹配。自定义分配器可以让 Wasm 模块更高效地管理有限的内存。

**性能敏感的后端服务：** 可以使用专门的分配器优化特定数据结构的分配模式，避免全局分配器的 thundering herd 问题。

## 工程实践建议

如果你现在就想开始使用自定义分配器，有几个值得注意的点。

**第一**，`Allocator` trait 是 unsafe trait——实现它需要手动保证 safety 约束。对于生产环境，优先使用社区已有的分配器 crate（如 `bumpalo`、`talc`），这些 crate 正在或即将适配新的稳定 API。

**第二**，`Vec<T, A>` 和 `Box<T, A>` 的类型签名发生了变化。如果你在公共 API 中暴露了 `Vec<T>`，升级到自定义分配器的版本意味着 API 的 breaking change。建议在内部实现中使用，等生态成熟后再纳入公开接口。

**第三**，当前只稳定了 `Box` 和 `Vec` 的 `new_in`，其他容器的支持还在路上。如果你需要 `HashMap<K, V, S, A>` 或 `String<A>`，短期内还需要依赖第三方方案或自行包装。

## 展望

`Allocator` trait 的稳定化本身是一个具体事件，但它反映了一个更长期的趋势：Rust 标准库正在从不必要的"一刀切"设计转向可组合、可定制的方向。和 `Allocator` 类似的还有正在推进的 `core::io`、`PathBuf::into_string`、`Vec::into_array`——标准库不再假设"所有用户都用全局默认配置"，而是逐步开放接口层，让用户按需替换组件。

对于关注 Rust 工程实践的团队来说，`Allocator` 的稳定化值得纳入下半年的技术规划。不是因为它会改变你每天写代码的方式，而是因为它会在你遇到性能瓶颈或内存约束时，提供一个标准化的、可维护的解决方案——而不是在每个项目里自己搓一套 unsafe 分配器抽象。
