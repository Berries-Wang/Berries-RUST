# Rust 的 build-std 终于要走向稳定了：从零编译标准库的最后冲刺

如果你用过 Rust 做嵌入式开发、交叉编译，或者尝试过减少标准库的二进制体积，那你一定对 `-Z build-std` 这个 nightly 参数不陌生。它让你能从头编译 Rust 标准库，而不仅仅是使用预编译的二进制版本。这个功能在 nightly 上已经存在了好几年，但一直没能在 stable 上落地。

现在这件事终于进入了最后冲刺阶段。

## 标准库编译这件事，和你想的不太一样

大多数 Rust 开发者日常使用的 `std`，是一个预编译好的静态库。你安装 Rust 时，rustup 会下载一份和你工具链版本匹配的标准库。这个过程非常方便——你只需写代码、编译，甚至不会意识到标准库的二进制文件是从哪里来的。

但对于某些场景来说，这个模型不够用。

嵌入式开发就是一个典型的例子：当你用 `thumbv7em-none-eabi` 这类 target 时，rustup 分发的 std 并不包含完整的标准库实现——很多目标根本连 pre-built 的 std 都没有。这背后的原因很简单：Rust 标准库有一部分平台相关代码（比如 `std::sys::unix` 或 `std::sys::windows`），当目标平台不在预编译列表里时，你就只能自己编译标准库。

另一个常见场景是交叉编译。比如你在 x86 的机器上给 aarch64 的目标编译，如果宿主和目标之间的 libc 版本或系统调用有差异，预编译的 std 可能就不能正常工作。你需要的是一份为目标平台量身编译的标准库。

还有一类需求来自性能优化和体积缩减：标准库的某些部分带有调试符号、断言检查或不必要的泛型特化，当你希望极致压缩输出体积时，能够控制标准库的编译参数就变得至关重要。

## build-std 到底做了什么

build-std 的本质是让 Cargo 在构建你的项目时，同步从源代码编译标准库。它接管了 `std`、`core`、`alloc`、`test` 这些 crate 的构建流程，把它们当作你项目依赖的一部分来处理。

这个功能通过一个 Cargo 参数来启用：

```bash
cargo build -Z build-std
```

加上这个参数后，Cargo 会做以下几件事：

1. 通过 rustup 组件 `rust-src` 获取标准库源码
2. 从源码开始编译 `core`、`alloc`、`std` 等 crate
3. 使用你当前工具链的编译器版本和优化参数
4. 将编译后的标准库链接到你的项目中

这意味着你可以用自己的编译参数来控制标准库的生成。比如：

```bash
cargo build -Z build-std=core,alloc \
  --target thumbv7em-none-eabi \
  -Z build-std-features=panic_immediate_abort
```

这段命令告诉 Cargo：只编译 `core` 和 `alloc`，不编译 `std`；目标平台是 ARM Cortex-M；遇到 panic 时直接 abort。这三个选项组合起来，可以让一个 Rust 嵌入式程序的体积从几十 KB 降到几 KB。

这种能力在当前的 stable Cargo 中是不存在的。如果你只用 `cargo build --target thumbv7em-none-eabi`，Cargo 只会去 rustup 的 sysroot 里找预编译的 std，如果没有就会报错。

## 为什么到现在才走向稳定

build-std 从 2019 年就进入了 nightly，但一直没法稳定，原因在于它触及了 Rust 工具链中几个根深蒂固的架构假设。

**第一个问题是 Cargo 和 rustc 之间的职责划分。** 传统上 Cargo 只负责编译你写的 crate，标准库由 rustup 提前安装好。build-std 模糊了这个界线——Cargo 需要知道标准库是哪个版本、从哪里获取源码、怎么处理标准库本身的 feature flags。

**第二个问题是稳定性保证。** 标准库的源码并不像普通 crate 那样遵循语义化版本。它的内部实现可能会在工具链升级时发生变化。build-std 需要确保无论标准库的内部结构如何变化，用它编译出来的程序和用预编译 std 编译出来的程序行为一致。

**第三个问题是平台兼容性。** 很多嵌入式 target 的 std 本来就是缺失的。build-std 需要处理的标准库「部分编译、部分不编译」的状态，在很多边缘 target 上行为并不确定。

这些问题在过去几个月里终于取得了实质性进展。

## 最近发生了什么

**RFC 3874** 和 **RFC 3875** 是 build-std 稳定的核心文档。前者定义了标准库从源码编译的方案，后者是对应的 Cargo 集成方案。RFC 3874 已经完成了最终评论期（FCP），即将正式合并。RFC 3875 的评审也已进入收尾阶段。

与此同时，Cargo 方面的实现已经开始。**PR #16675** 在 Cargo 仓库中提交了 build-std 核心变更的初期原型。这个 PR 涉及了 Cargo 内部如何识别标准库 crate、如何获取标准库源码、如何在构建图中插入标准库节点等核心逻辑。虽然还在早期阶段，但它的存在意味着 Cargo 团队已经开始认真对待这个功能的落地了。

从项目目标的层面来看，build-std 在 **2025H2 的项目目标**中被列为旗舰级目标，由 Cargo 团队、编译器团队和标准库团队联合推进。Cargo 团队的 Eric Huss、编译器团队的 David Wood 和标准库团队的 Amanieu d'Antras 分别作为各自团队的负责人。三方的联合推进意味着之前提到的职责划分问题已经得到了充分的协调。

在最近的进度更新中，项目负责人提到 Adam Gemmell 已经和 Cargo 团队进行了多轮反馈沟通，正在根据 review 意见调整 PR 的实现方向。与此同时，David Wood 也在推动 RFC 两阶段方案的最终合并。

## 这会改变什么

build-std 的稳定，对于不同场景的开发者意味着不同的事情。

**对于嵌入式开发者来说，** 这是最直接的受益者。不再需要依赖 rustup 为特定 target 提供预编译的 std，也不再需要在 nightly 上冒着不稳定的风险使用 `-Z build-std`。一个稳定的 build-std 意味着在任何 Rust 支持的目标上，你都可以通过一行 Cargo 配置完成标准库的编译。

**对于做交叉编译的团队来说，** 它消除了一个常见的痛点：在 x86 macOS 上为 Linux aarch64 目标编译时，标准库的 glibc 版本不匹配问题可以通过 build-std 来解决。编译标准库时使用目标平台的系统库，而不是宿主平台的，这从根本上解决了 ABI 不匹配的问题。

**对于关注二进制体积的项目，** build-std 稳定后，`panic_immediate_abort`、`optimize_for_size` 这类标准库编译时选项将成为稳定的配置手段。你可以放心地在 release 配置中打开这些选项，而不必担心 nightly 的稳定性风险。

**对于标准库本身，** 这也意味着更健康的开发循环。当 build-std 成为稳定的基础设施后，更多开发者可以更容易地测试标准库修改对自身项目的影响，从而更积极地参与标准库的改进。

## 现在可以做什么

虽然 build-std 尚未稳定，但从现在开始布局是合理的。

**第一，确认你的项目是否能用 build-std 改善编译或运行效果。** 对于嵌入式或 no_std 项目，可以尝试在 nightly 上使用 `cargo build -Z build-std=core`，评估二进制体积和编译时间的变化。

**第二，关注 feature 配置。** build-std 支持通过 `-Z build-std-features` 传递标准库特性标识。`panic_immediate_abort` 是最常用的一个，此外还有 `optimize_for_size` 等选项。了解这些选项的效果，等稳定后就能直接应用。

**第三，如果维护的是自定义 target 或交叉编译配置，** 可以开始研究 target JSON 文件中如何配合 build-std 工作。build-std 对 target 的描述信息有一定要求——需要正确的链接器、CPU 特性、ABI 规范等信息，这些在 target JSON 中定义。

构建系统层面的准备也值得做。build-std 稳定后，`.cargo/config.toml` 中预计会新增对应的配置键。目前 nightly 上可以通过 `unstable.build-std` 键来配置默认的标准库 crate 列表，稳定后的配置语法可能会类似：

```toml
[target.thumbv7em-none-eabi]
build-std = ["core", "alloc"]
```

提前了解这些配置模式，可以帮助团队在功能稳定后快速切换。

build-std 是一个在 Rust 社区中存在已久但因为技术挑战迟迟没能稳定的功能。现在它走到了最后阶段：RFC 已达成共识，Cargo 实现已启动。从牛刀小试到日常可用，这次是真的近了。
