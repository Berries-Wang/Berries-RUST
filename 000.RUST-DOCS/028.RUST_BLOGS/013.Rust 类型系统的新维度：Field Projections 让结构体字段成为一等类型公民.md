# Rust 类型系统的新维度：Field Projections 让结构体字段成为一等类型公民

Rust 的类型系统在表达能力上一直走在一条持续演进的道路上——从泛型到关联类型，从 GAT 到 const 泛型，每一步都在扩展开发者能用类型表达的范围。但有一个空白始终存在：你无法在泛型代码中「提到」结构体的某个具体字段。

这在实践中意味着什么？如果你写过 Pin 投影的安全封装、做过基于字段的序列化、或者尝试在框架层面实现类似 ORM 的字段映射，你一定遇到过这个瓶颈——最终要么靠过程宏生成样板代码，要么靠 unsafe 手工计算偏移量。不是做不到，而是类型系统在这一层帮不上忙。

**Field Projections（字段投影）** 语言实验正在填补这个空白。最近合并的第一个 PR（rust-lang/rust#152730）带来了 `field_of!` 宏和 `Field` 特征，让 Rust 的类型系统第一次能够「看见」结构体的每一个字段，并以类型的方式与它们交互。

## 从语法提案到类型系统基础设施

Field Projections 的探索并非始于昨天。最早期的讨论围绕「用 `@` 语法标记投影路径」展开，尝试从语法层面为 Pin 投影提供一个安全、显式的表达方式。但深入设计后发现，这不仅仅是语法糖的问题——真正的障碍在于，Rust 的类型系统缺少对「字段」这个层级的概念抽象。

你可以在泛型中约束一个类型 `T`，可以约束一个关联类型 `Item`，甚至可以约束一个 const 泛型 `N`，但你无法说「这个函数的参数是 `Struct` 的那个字段」。这不是语法层面的缺失，而是类型系统概念层面的缺失。

新方案绕过了语法优先的思路，转而从**类型系统基础设施**入手：先让编译器为每个字段生成一个独一无二的类型，再通过这些类型暴露字段的元信息（偏移、类型、所属结构体）。至于语法——那是之后的事情。

## `field_of!` 宏：让每个字段拥有自己的类型

`field_of!` 是这套方案的核心入口。它在编译期为结构体的每个字段生成一个「字段代表类型」（Field Representing Type，FRT）。这些类型是编译器生成的、匿名的、对开发者透明的新类型，但它们的存在是真实可感的——你可以把它们当作类型参数传进泛型函数。

```rust
#![feature(field_projections)]

use std::field::{Field, field_of};
use std::ptr;

fn project_ref<'a, T, F: Field<Base = T>>(r: &'a T) -> &'a F::Type {
    // SAFETY: `Field` 保证偏移和类型匹配
    unsafe { &*ptr::from_ref(r).byte_add(F::OFFSET).cast() }
}

struct Struct {
    field: i32,
    other: u32,
}

fn main() {
    let s = Struct { field: 42, other: 24 };
    let f = project_ref::<_, field_of!(Struct, field)>(&s);
    let o = project_ref::<_, field_of!(Struct, other)>(&s);
    println!("field: {f}"); // 42
    println!("other: {o}"); // 24
}
```

在这个例子里，`field_of!(Struct, field)` 返回的是一个**类型**，而不是一个值。它实现了 `Field` 特征，提供了 `Base`（所属结构体）、`Type`（字段类型）和 `OFFSET`（字节偏移）。`project_ref` 函数不关心你传进来的是哪个字段——只要它是 `Field<Base = T>`，它就能正确计算出指向那个字段的引用。

这看起来像是小步前进，但它的意义在于：这行代码之前，Rust 的泛型系统中没有一个合法的表达式能表示「`Struct` 的 `field` 字段」。而现在，`field_of!(Struct, field)` 是一个类型，你可以把它写在尖括号里。

## 可扩展性：字段的「标注」机制

FRT 更强大的特性在于：如果拥有结构体的所有权——也就是你能定义这个结构体——你就可以为它的字段类型实现 trait。这意味着你可以为字段附加信息，扩展 `Field` 特征的能力。

Pin 投影是一个典型场景。在异步 Rust 中，自引用结构体的字段投影一直是个痛点——`Pin<&mut T>` 的某些字段可以安全地投影出 `Pin<&mut FieldType>`，某些不行。目前的做法是靠 unsafe 手工实现，容易出错且难以复用。

通过 FRT，你可以定义一个 `PinnableField` trait：

```rust
use std::pin::Pin;

unsafe trait PinnableField: Field {
    type StructuralRefMut<'a>
    where
        Self::Type: 'a,
        Self::Base: 'a;

    fn project_mut<'a>(
        base: Pin<&'a mut Self::Base>,
    ) -> Self::StructuralRefMut<'a>
    where
        Self::Type: 'a,
        Self::Base: 'a;
}
```

然后为结构体中的可投影字段实现它。编译器知道这个字段的偏移和类型，Pin 的安全性通过 trait 约束在类型层面得到保证。

这对异步 Rust 的影响尤其深远——它意味着 Pin 投影的安全封装不再需要过程宏，不再需要 `pin_project` crate，类型系统自己就能承担这个职责。

## 更广阔的应用场景

Pin 投影是 Field Projections 最直接的应用场景，但不是唯一的。

**序列化框架。** 当前的 serde 靠派生宏读取每个字段，宏生成的代码无法在字段级别做泛型抽象。如果有 FRT，序列化框架可以在泛型层面表达「遍历一个结构体的所有字段，对每个字段调用序列化函数」——这不再是宏的专属能力。

**ORM 和数据库映射。** 类似地，从数据库行映射到结构体字段的代码，可以写成在字段类型上的泛型函数，而不是在派生宏里逐字段展开。

**GUI 状态管理。** 状态绑定需要把 UI 组件和结构体的特定字段关联起来。FRT 让这种关联变成类型安全的，编译器可以检查你绑定的是不是正确的字段。

**编译期自省。** 目前 Rust 的自省能力集中在类型层面（`TypeId`、`Any`），没有「字段列表」的概念。FRT 和 `Field` 特征为编译期自省提供了一个新的维度——虽然还不完整，但方向是清晰的。

## 当前状态与路线图

需要明确的是，这仍然是 nightly-only 的实验性功能，距离稳定还有相当长的路。当前阶段的目标是让语言团队和社区能够通过实际使用来验证 FRT 设计的合理性。

**已实现的能力：**

- `field_of!` 宏为 struct（非 `repr(packed)`，字段均为 `Sized`）生成 FRT
- `Field` 特征暴露 `Base`、`Type`、`OFFSET`
- 可以为 FRT 实现自定义 trait

**已知限制：**

- 尚不支持 `repr(packed)` 结构体
- 尚不支持 unsized 字段
- 不支持 enum 变体的字段投影（虽然在规划中）
- `field_of!` 目前只能用于路径中的最后一个字段——如果是嵌套结构体，还不能一次性投影到嵌套子字段的类型

**下一步的探索方向**包括：解决自动引用（autoref）和方法解析在字段投影世界的兼容性问题；设计最终的用户可见语法；以及最重要的——将 FRT 与借用检查器集成，让 `Pin<&mut T>` 的字段投影在借用层面得到安全保障。

## 为什么值得关注

Field Projections 不是那种明天就能用的特性，但它代表了 Rust 类型系统对「现实世界代码结构」的一次重要抽象升华。

过去十年，Rust 在泛型、特征、生命周期方面构建的能力，解决了「类型」层面的泛型问题。但一个类型内部的「字段」始终是个盲区——你的代码无法在泛型层面描述「某个类型的某个字段」。Field Projections 正在打开这扇门。

对于编写框架和基础设施的团队来说，这意味着更少的过程宏、更多的类型安全检查、更少的运行时开销。对于日常业务开发来说，这意味着最终——当这个功能稳定之后——很多今天需要派生的样板代码可以被更自然的泛型代码替代。

这不是一个语法糖级别的改进，而是类型系统能力的边界拓展。如果说过程宏让 Rust 获得了「编译期代码生成」的能力，那么 Field Projections 让类型系统获得了「在字段维度上编程」的能力——后者是前者无法替代的。

# Rust 字段投影（Field Projections）初探：当编译器开始理解字段本身

Rust 的项目目标更新中，Field Projections（字段投影）作为"Beyond &"旗舰目标下的关键子项取得了实质性进展。`field_of!` 宏和 `Field` trait 已经合入 nightly，lang team 设计会议给出了极其正面的评价。这一特性将从根本上改变 Rust 处理结构体字段的方式——从 Pin 投影到泛型字段操作，可能是 Rust 类型系统下一个最值得关注的方向。

## 一个长期被忽略的盲点

写过 Rust 的人都有过这样的体验：当你需要以泛型方式处理一个结构体中的某个字段时，几乎无路可走。Rust 的 trait 系统可以对类型进行抽象，但对"结构体里的某个字段"这个层次的概念毫无支持。

这个问题在多个场景下反复出现：

**第一个是 Pin 投影。** 当你写一个自引用结构体时，需要手动为每个 Pin 住的字段编写 unsafe 的投影方法。这不仅容易出错，而且代码高度重复。标准库的 `Pin::new_unchecked` 几乎是唯一工具，而它的安全性完全取决于开发者能否正确地标记"哪些字段可以被 Pin 投影"。

**第二个是字段级别的借用检查。** 当前借用检查器把整个结构体当作一个整体来处理——借用了字段 A 就不能再借用字段 B？这在很多情况下其实是安全的，但编译器无法区分。

**第三个是泛型字段操作。** ORM 框架、序列化库、Builder 模式——所有这些场景都需要某种形式的"按字段名操作"，目前要么靠宏展开硬编码，要么靠运行时反射（如 anyhow），没有一个类型安全的泛型方案。

Field projections 试图从根本上解决这些问题。

## 什么是 Field Representing Types

这次合入 nightly 的核心是一个看似简单但影响深远的概念：**每个结构体字段都会获得一个唯一的类型**。

```rust
#![feature(field_projections)]
use std::field::{Field, field_of};

struct Config {
    timeout: u32,
    retries: u32,
    endpoint: String,
}

// field_of! 宏为每个字段生成唯一的类型
// field_of!(Config, timeout) 生成一个唯一的类型
// field_of!(Config, retries) 生成另一个唯一的类型
```

这些通过 `field_of!` 生成的类型被称为 **Field Representing Types（FRTs）**。它们自动实现了 `Field` trait，暴露三个关键信息：

- `Field::Type`：字段本身的类型
- `Field::Base`：字段所属的结构体类型
- `Field::OFFSET`：字段在结构体中的字节偏移量

这意味着你在泛型代码中可以这样写：

```rust
fn project_ref<'a, T, F: Field<Base = T>>(r: &'a T) -> &'a F::Type {
    unsafe {
        &*ptr::from_ref(r)
            .byte_add(F::OFFSET)
            .cast()
    }
}

let cfg = Config { timeout: 30, retries: 3, endpoint: "https://api.example.com".into() };
let timeout: &u32 = project_ref::<_, field_of!(Config, timeout)>(&cfg);
```

每次对 `field_of!(Config, timeout)` 的调用都产生一个在编译期完全确定的类型，偏移量信息嵌入到 trait 的关联常量中，没有任何运行时开销。这本质上就是在类型层面给每个字段发了一张身份证。

## 最直接的收益：安全的 Pin 投影

Field projections 最直接的推动力来自 Pin 的 ergonomics 问题。当前如果你有一个自引用结构体：

```rust
struct SelfReferential {
    data: String,
    // 这个字段被 Pin 住，不能移动
    pinned_field: u32,
}
```

要为 Pin 实现安全的投影，你需要写大量 unsafe 代码，而且要确保"哪些字段是 Pin 的"这个语义在类型层面得到表达。有了 FRTs 之后，你可以为单个字段实现一个 `PinnableField` trait：

```rust
unsafe trait PinnableField: Field {
    type StructuralRefMut<'a>: 'a
    where Self::Type: 'a, Self::Base: 'a;

    fn project_mut<'a>(
        base: Pin<&'a mut Self::Base>
    ) -> Self::StructuralRefMut<'a>
    where Self::Type: 'a, Self::Base: 'a;
}

// 对普通字段：投影出 &mut T
unsafe impl PinnableField for field_of!(SelfReferential, data) {
    type StructuralRefMut<'a> = &'a mut String;
    fn project_mut<'a>(
        base: Pin<&'a mut Self::Base>
    ) -> Self::StructuralRefMut<'a> {
        unsafe { &mut Pin::into_inner_unchecked(base).data }
    }
}

// 对 pinned 字段：投影出 Pin<&mut T>
unsafe impl PinnableField for field_of!(SelfReferential, pinned_field) {
    type StructuralRefMut<'a> = Pin<&'a mut u32>;
    fn project_mut<'a>(
        base: Pin<&'a mut Self::Base>
    ) -> Self::StructuralRefMut<'a> {
        unsafe { Pin::new_unchecked(&mut Pin::into_inner_unchecked(base).pinned_field) }
    }
}
```

这里的核心区别在 `StructuralRefMut` 的返回类型上：普通字段返回 `&mut T`，pinned 字段返回 `Pin<&mut T>`。调用者无需关心哪个字段被 Pin 住——类型系统自动保证了安全性。通过 proc macro 可以进一步自动化这些实现，开发者只需要在字段上加一个 `#[pinned]` 属性即可。

## 不止于 Pin：更广阔的想象空间

虽然 Field projections 当前最紧迫的驱动力是 Pin 的 ergonomics，但它的应用范围远不止于此。

**对于序列化框架：** serde 的 `Serialize` 和 `Deserialize` 当前对每个字段的处理都是在 derive 宏展开时硬编码的。如果能以泛型方式描述"枚举结构体的所有字段"，框架可以更灵活地支持自定义序列化策略，而不需要大量使用属性宏。

**对于 ORM：** Rust 的 ORM 框架（如 Diesel、SeaORM）目前依赖大量的宏和代码生成来处理字段映射。如果字段本身是一等类型，字段级别的查询构建就可以写成泛型函数，而非宏展开的代码生成。

**对于状态机模式：** Typestate pattern 中，结构体在不同状态有不同字段组合。当前的做法是用多个结构体或 `PhantomData` 来编码状态。如果字段可以按需存在或消失，状态转变可以表达得更自然。

**对于借用检查器的改进：** 这是更长远的影响。如果借用检查器能理解"某个借用只覆盖了结构体的部分字段"，理论上可以实现更细粒度的借用——不同的函数参数借用同一个结构体的不同字段时可以并行执行。这正是 View Types 项目的终极目标，而 Field projections 提供了底层机制。

## 实验状态与路线图

目前这个特性处于 lang experiment 阶段，需要 `#![feature(field_projections)]` 开启。它的功能还很有限，不支持嵌套字段、不支持 `repr(packed)` 结构体、enum 字段的 FRT 不实现 `Field` trait。

后续路线图清晰分为三条线：

**形式化验证（a-mir-formality）：** 在形式化模型中验证借用检查器改动是否正确。这部分依赖于 Niko Matsakis 开发的新的基于表达式的语法。

**编译器实现：** 持续改进 FRTs，探索可能的 desugaring 方案，编写 proc macro 自动化工具。逐步从标准库层面的 trait 扩展到编译器内置支持。

**实验验证：** 在 Linux 内核、Crubit、标准库等真实项目中测试 Field projections 的实用性。

预计年内会看到实验性功能在 nightly 上的持续迭代和扩充，但距离稳定化还有相当距离。

## 为什么值得关注

Rust 的趋势一直是在类型系统中把隐式约定变成显式约束——生命周期从 `'static` 假设变成显式标注，Send/Sync 从无到有，Pin 从不安全约定变成类型强制。Field projections 延续了这一趋势，把"结构体里的字段"这样一个在几乎所有语言中都是"纯运行时概念"的东西，提升到了类型系统层面。

对于 Rust 开发者来说，这意味着：

- 未来处理 Pin 时不再需要手写大量 unsafe 代码
- 框架和库可以在类型层面安全地操作字段，而不仅仅依靠宏展开
- 借用检查器能理解更细粒度的借用关系

当然，这还是一个正在孵化的特性。但方向已经明确、设计已经获得共识、代码已经开始落地。对于关注 Rust 语言演进的人来说，Field projections 是未来几年最值得跟踪的进展之一。

# Rust 的类型系统开始理解结构体字段：field_of! 宏与 Field Projections 解读

如果你用 Rust 写过需要大量操作结构体字段的代码，很可能遇到过这类场景：想写一个函数，只操作某个结构体的特定字段，但类型系统不允许你表达"这个参数是结构体的某个字段"。你只能重复写 N 个几乎相同的函数，或者退回到宏展开。

过去几个月，Rust 的编译器团队在"Field Projections"语言实验上取得了实质性进展。最近合入 nightly 的 `field_of!` 宏，为每个结构体字段生成了独一无二的类型——这是 Rust 类型系统第一次能以精确的方式"看见"结构体内部的字段。

## 一个长期存在的盲区

Rust 的类型系统对结构体字段一直处于"黑盒"状态。你可以访问字段，可以在模式匹配中解构，但无法在类型层面表达"这个类型是结构体 X 的字段 Y"。

举个例子，假设你有一个包含多个字段的结构体，想为每个字段计算偏移量并做安全访问：

```rust
struct Config {
    timeout: u32,
    retries: u32,
    endpoint: String,
}
```

在 Rust 中，你无法写一个泛型函数来统一处理这些字段的偏移计算。`offset_of!` 宏可以给出某个字段的偏移，但它是在编译期计算，不产生类型层面的信息。你无法写一个函数，接受"任意字段"作为类型参数，然后根据字段的偏移来操作。

这不仅仅是语法糖的问题。缺乏字段级别的类型抽象，意味着：

- 每次新增字段，相关代码都要手动同步
- Pin 投影需要大量 unsafe 代码，且缺乏编译器检查
- 字段级借用（只借用结构体的某个字段，而非整个结构体）无法通过类型系统表达

## `field_of!` 宏：为每个字段分配一个类型

最近合入 nightly 的 PR #152730 引入了"Field Representing Types"（FRT，字段表示类型）。这是 Field Projections 语言实验的第一步，跟踪问题为 #145383。

核心接口定义在 `core::field` 模块中：

```rust
// core::field

pub unsafe trait Field {
    /// 包含该字段的结构体类型
    type Base;

    /// 字段本身的类型
    type Type;

    /// 字段在结构体中的字节偏移
    const OFFSET: usize;
}

/// 产生字段表示类型的宏
pub macro field_of($Container:ty, $($fields:expr)+ $(,)?);
```

`field_of!` 宏接受一个结构体类型和一个字段名，展开为一个独一无二的类型。这个类型实现了 `Field` trait，暴露了字段的元信息（基类型、字段类型、字节偏移）。

来看一个实际的用法：

```rust
#![feature(field_projections)]

use core::field::{Field, field_of};
use core::ptr;

fn project_ref<'a, T, F: Field<Base = T>>(r: &'a T) -> &'a F::Type {
    // Safety: Field trait 保证偏移是正确的
    unsafe { &*ptr::from_ref(r).byte_add(F::OFFSET).cast() }
}

struct MyStruct {
    field: i32,
    other: u32,
}

fn main() {
    let s = MyStruct { field: 42, other: 24 };
    let field = project_ref::<_, field_of!(MyStruct, field)>(&s);
    let other = project_ref::<_, field_of!(MyStruct, other)>(&s);
    println!("field: {field}");  // 输出 42
    println!("other: {other}");  // 输出 24
}
```

这段代码的精髓在于：`field_of!(MyStruct, field)` 产生了一个**类型**，它承载了"field 是 `MyStruct` 中以某个偏移量存在的 `i32` 字段"这一信息。`project_ref` 函数不关心具体是哪个字段，它只要求"给我一个字段，我就能从基类型的引用中得到对字段的引用"。

## 从字段类型到字段标注

FRT 的真正威力，在于你可以为字段类型实现 trait。因为 `field_of!` 产生的类型是你的代码可以"命名"的，你可以在自己的 crate 中给它们添加标注。

Rust-for-Linux 团队已经利用这个能力构建了 `PinnableField` trait，用于标注结构体中哪些字段是"结构体钉住"（structurally pinned）的：

```rust
use core::field::Field;

/// 标记一个字段是结构体钉住的
///
/// Safety: Projected 类型要么是 Pin<&'a mut Self::Type>
/// （表示该字段是结构体钉住的），要么是 &'a mut Self::Type
pub unsafe trait PinnableField: Field {
    type Projected<'a>
    where
        Self::Type: 'a;

    unsafe fn from_pinned_ref(r: &mut Self::Type) -> Self::Projected<'_>;
}
```

有了这个 trait，结构体可以声明哪些字段是"钉住"的，哪些不是：

```rust
struct SelfReferential {
    data: Vec<u8>,
    // 这个字段是结构体钉住的——不能移动
    view: *const u8,
}

// 为 view 字段实现 PinnableField，标记它需要 Pin 保护
unsafe impl PinnableField for field_of!(SelfReferential, view) {
    type Projected<'a> = Pin<&'a mut *const u8>;

    unsafe fn from_pinned_ref(r: &mut *const u8) -> Pin<&'a mut *const u8> {
        Pin::new_unchecked(r)
    }
}
```

在传统的 Rust 中，`SelfReferential` 这类自引用结构体的 Pin 投影需要大量手写 unsafe 代码，每一处都要人工确保正确性。而 FRT 让编译器能够理解"这个字段标记了 Pin 语义"，为后续的自动检查铺平了道路。

## 从宏到类型系统的完整路径

Field Projections 的完整图景并不仅仅是 `field_of!` 这一个宏。它实际上包含了三个层次的工作：

**第一层是字段表示类型（FRT）**，也就是 `field_of!` 宏和 `Field` trait。这是目前在 nightly 上已经可用的部分。它让类型系统能够"命名"一个字段，并获取字段的元信息。

**第二层是字段投影操作**，包括读取、写入、借用和析构等操作的 trait 化。这些 trait 定义了如何在基类型上安全地操作字段，是 a-mir-formality 项目中形式化建模的核心内容。

**第三层是借用检查器集成**，这是最终目标：让借用检查器理解"我只借用了结构体的字段 A，而不是整个结构体，因此同时借用字段 B 是安全的"。这是 View Types 概念的核心，也是 Rust 多年来一直想做但未能做到的事情。

目前第一层已经落地，第二层正在 a-mir-formality 中建模，第三层仍在探索阶段。但第一层的落地已经打开了足够多的可能性——Rust-for-Linux 团队已经在 lang-experiment 分支上构建了基于 FRT 的完整字段投影库。

## 为什么这件事值得关注

Field Projections 处在 Rust 几个重要方向的交汇点上。

**Pin 的长期痛点。** Pin 是 Rust 异步编程中无法回避的概念。自引用结构体需要 Pin 来保证安全，但 Pin 的投影操作一直缺乏编译器支持。`Pin::new_unchecked` 和 `Pin::as_mut` 的手动正确性检查是 unsafe 代码的主要来源之一。FRT 让编译器能够理解"这个字段是结构体钉住的"，这是 Pin 投影从"人工检查"走向"编译器验证"的关键一步。

**字段级借用的工程价值。** 目前的借用检查器以整个结构体为粒度——如果你借用了结构体的某个字段，整个结构体在借用期间都不可变。但很多场景下，你只需要操作结构体的一小部分。字段级借用（View Types）能显著提升 Rust 在系统编程中的表达能力，而 FRT 提供了实现字段级借用的类型系统基础设施。

**与 Rust-for-Linux 的结合。** Linux 内核中的 Rust 代码大量使用自引用结构体和 Pin 投影。内核团队对 Field Projections 有直接需求，这也是为什么 Rust-for-Linux 团队深度参与了这项功能的开发，并且在 FRT 落地后立即开始构建基于它的字段投影库。

## 当前状态与使用方式

`field_of!` 宏和 `Field` trait 目前处于 nightly 独占状态，需要通过 `#![feature(field_projections)]` 启用。

```toml
# 在 Cargo.toml 中 [dependencies] # 目前无需额外依赖
```

```rust
// 在 crate 根节点
#![feature(field_projections)]
```

需要说明的是，这仍然是一个活跃演化中的实验性功能。`Field` trait 的 API 可能会在未来发生变化，`field_of!` 宏的语法也可能会调整。嵌套字段（如 `field_of!(Outer, inner.field)`）暂不支持，但已经在路线图上。

对于大多数 Rust 开发者来说，现在不需要立刻在自己的项目中使用 FRT。但理解它的设计方向，有助于把握 Rust 类型系统正在经历的这场范式转变——从"结构体是一个黑盒"到"类型系统能理解结构体的内部结构"。

## 总结

`field_of!` 宏的合入，标志着 Rust 在"类型系统感知字段"这条路上迈出了实质性的一步。Field Representing Types 让编译器第一次能够以精确的类型信息来指代结构体的字段，而不仅仅是靠宏展开或运行时反射。

对于团队来说，这意味着 Rust 正在补齐类型系统中一个长期的缺失。Pin 投影、字段级借用、自引用结构体——这些曾经需要大量 unsafe 代码和人工审查才能解决的问题，正在逐步走向编译器支持的工程化路径。这门语言对"结构体"的理解，正在从"数据的容器"进化为"有类型结构的实体"。
