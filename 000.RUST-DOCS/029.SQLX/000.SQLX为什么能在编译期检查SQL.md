# SQLX 为什么能在编译期检查 SQL

> 来源：微信公众号文章《Rust sqlx 为什么能在编译期检查 SQL》，结合本仓库（rust-lang/rust 1.96.0 源码树）中的 rustc 侧源码对照整理。
> 源码引用原则：**优先引用当前仓库本地路径**（rustc 侧全部本地可读，另附 [GitHub 1.96.0](https://github.com/rust-lang/rust/tree/1.96.0) 链接，行号以本地快照为准）；sqlx 不在本仓库（`Cargo.toml`/`Cargo.lock` 均无），只能 GitHub 线上引用，其机制可用仓库内同类过程宏实例替代学习（见下文专门一节）。

`query!` 不是编译器插件，而是一个**过程宏**：它在 rustc 展开阶段被调用，此时它只是一段普通 Rust 代码，可以联网、连数据库，拿 `DESCRIBE users` 的真实类型表去匹配 Rust 类型，匹配成功才生成代码；生成的代码里埋了一句 `if false { let _: &i32 = &id; }` 的"假绑定"，让 rustc 正常类型检查替它把最后一道关。

**做校验的是 sqlx（协议层），做兜底的是 rustc（类型层）。**

## 三个问题的答案

| 问题 | 机制 | 关键源码（sqlx） |
|-|-|-|
| 执行时机？ | cargo 两阶段构建：先把 `sqlx-macros` 编译成 dylib；编译用户 crate 时 rustc 在**类型检查之前**的展开阶段加载并调用它 | [sqlx-macros-core/src/lib.rs](https://github.com/launchbadge/sqlx/blob/main/sqlx-macros-core/src/lib.rs) |
| 怎么知道列类型？ | 宏内部用**运行时同一套驱动**真连数据库，发 `DESCRIBE` / `sqlite3_prepare` 拿 OUTPUTS + 参数类型 | [sqlx-macros-core/src/query/verify.rs](https://github.com/launchbadge/sqlx/blob/main/sqlx-macros-core/src/query/verify.rs) |
| 怎么"算"类型？ | sqlx 自己的类型匹配只决定**生成什么**；rustc 的类型检查决定**能不能编译过**——生成的 `if false` 假绑定把字段类型反向锚定到用户变量上 | [sqlx-macros-core/src/query/output.rs](https://github.com/launchbadge/sqlx/blob/main/sqlx-macros-core/src/query/output.rs) |

## 全链路流程图

```
cargo build
│
├─ 阶段1: 并行构建依赖, sqlx-macros(过程宏crate)
│         编译为 libsqlx_macros.so ──────────────┐
│                                                │
└─ 阶段2: rustc main.rs                          ▼
     │
     ├─ 解析成 AST, query!("...", id) 只是宏调用节点
     │
     ├─【展开阶段】 expand_crate            passes.rs:219
     │    fully_expand_fragment 不动点循环  expand.rs:493
     │      ├─ dlsym 加载 dylib, 取出        creader.rs:921
     │      │   __rustc_proc_macro_decls 符号表
     │      ├─ TokenStream 序列化过 bridge   client.rs:247
     │      │   (extern "C", 宏与rustc同进程)
     │      ├─ 宏内: 连库 → DESCRIBE →      verify.rs
     │      │   map bind param types → 校验
     │      │   不匹配 → span_err, 编译中止
     │      └─ 返回生成代码, 递归展开直至无宏调用
     │
     ├─ resolve_crate / lower_to_hir        passes.rs:305 / :883
     │
     └─【analysis 类型检查】                  passes.rs:1179
          if false { let _: &i32 = &id; }
          → 与普通代码同等 typeck
          → 用户变量类型与列类型不符 → E0308
```

## rustc 侧源码（为什么这整套是可能的）

| 环节 | 本地路径 | 作用 |
|-|-|-|
| 加载过程宏 dylib | `compiler/rustc_metadata/src/creader.rs:921`（[GitHub](https://github.com/rust-lang/rust/blob/1.96.0/compiler/rustc_metadata/src/creader.rs)）`dlsym_proc_macros`，`:1415 load_dylib` | 用 libloading 打开 dylib，`load_symbol_from_dylib::<*const &[ProcMacro]>` 取出导出的宏注册表——**过程宏就是一段被 rustc dlopen 进来执行的普通 Rust 代码**，所以它能做任何 I/O（连数据库） |
| 调用入口 | `compiler/rustc_expand/src/proc_macro.rs:27`（[GitHub](https://github.com/rust-lang/rust/blob/1.96.0/compiler/rustc_expand/src/proc_macro.rs)）`BangProcMacro::expand` | `query!` 这类函数式宏走这里：`self.client.run(&strategy, server, input, …)` |
| AST↔TokenStream 转换服务 | `compiler/rustc_expand/src/proc_macro_server.rs`（[GitHub](https://github.com/rust-lang/rust/blob/1.96.0/compiler/rustc_expand/src/proc_macro_server.rs)） | rustc 侧的 bridge server：宏拿到的 `TokenStream`、`Span`（`call_site`/`def_site`，报错定位靠它）都由它翻译 |
| C ABI 桥 | `library/proc_macro/src/bridge/client.rs:247`（[GitHub](https://github.com/rust-lang/rust/blob/1.96.0/library/proc_macro/src/bridge/client.rs)）`run_client`，`:303 expand1` | 输入编码进 buffer → `state::set(\|\| f(input))` 真正执行宏函数 → 输出编码返回；这也是 sqlx 的 `span_err` 能以正常编译错误形式冒出来的通道 |
| 展开不动点循环 | `compiler/rustc_expand/src/expand.rs:493`（[GitHub](https://github.com/rust-lang/rust/blob/1.96.0/compiler/rustc_expand/src/expand.rs)）`fully_expand_fragment` | 收集所有宏调用→替换占位符→逐个展开→**输出片段再递归展开**直到没有宏调用。`query!` 生成的代码里若还有宏，继续在此循环展开 |
| 时序保证 | `compiler/rustc_interface/src/passes.rs:219, :303, :305, :883, :1179`（[GitHub](https://github.com/rust-lang/rust/blob/1.96.0/compiler/rustc_interface/src/passes.rs)） | `expand_crate`("Expand macros now!") → "Done with macro expansion!" → `resolve_crate` → `lower_to_hir` → `analysis`(typeck)。**展开严格先于类型检查**，所以宏能先"验一道"，类型检查再"兜一道" |

两个值得注意的细节：

- **同进程执行**：`compiler/rustc_expand/src/proc_macro.rs:15` 的 `MaybeCrossThread` 策略说明宏在 rustc 进程内跑，这也解释了"libsqlite3-sys 在宿主机上执行"——`DESCRIBE` 走的是宿主机网络栈，与目标平台无关。
- **`if false` 假绑定为何有效**：rustc 的 `analysis` 阶段对函数体做完整 typeck，不做可达性剪枝（dead_code 是之后的 lint）。`&'param T` 的生命周期参数把"借用必须在语句存活期间有效"这条规则带进来：绑定参数按引用传入，语句 drop 前引用必须一直有效（与借用检查衔接）。

## 易混淆点（文章的"考据"结论）

- `query_as!(Users, ...)` 看起来像属性宏，其实是**函数式宏**——`Users` 只是一个 token 参数，不是注解。
- `from_row` 方法来自 `#[derive(FromRow)]`，这才是 **derive 宏**（在 rustc 侧对应 `compiler/rustc_expand/src/proc_macro.rs:90` 附近的 `expand_derive_proc_macro_outer` 路径）。
- sqlx **不是编译器插件**，它用的全是稳定的过程宏 API；驱动也不是绕过协议，而是复用运行时同一套实现。

## 陷阱（工程实践）

| 陷阱 | 原因与对策 |
|-|-|
| `DATABASE_URL` 缺失直接报错 | 宏需要真连库；CI/离线环境用 `cargo sqlx prepare` 生成 `.sqlx` 缓存 + `SQLX_OFFLINE=true` |
| 改了 SQL 但编译还是旧的 | `.sqlx` 缓存未更新，重新执行 `cargo sqlx prepare` |
| `query_as!` 的结构体字段不匹配 | derive 的 `FromRow` 按名匹配，缺字段/多字段/类型不符都会在编译期暴露 |

## 复现实验

- 把 SQL 改成 `SELECT id, version FROM users WHERE id = ?` 再传 `&id`（i32）→ 先在 sqlx 校验层报**参数类型错**。
- 把 `query!` 换成 `version()` 但变量仍是 `id` → 由 rustc typeck 报 **E0308**。两者正好对应"两道关"各自拦截的场景。
- `cargo expand` 可直接看到生成的假绑定代码。
